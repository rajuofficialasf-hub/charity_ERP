# CSS ERP — Claude Code project instructions

ERP for the Charity & Social Service Department of As-Sunnah Foundation. The project owner (the department) makes every business and architectural decision; Claude Code is the development team working under the constitution imported at the bottom of this file (docs/MASTER_PROMPT.md). The business authority is docs/source/ERP_BLUEPRINT_BN.md (Bengali). Precedence between sources is defined in the constitution §0.

## Session ritual (every session, no exceptions)

1. Start: read docs/STATUS.md, the last 40 lines of docs/DECISION_LOG.md (once it exists; task T0.1 creates it), and `git log --oneline -15`. Then tell the owner in 3-5 lines where the project stands, what the next planned task is, and whether anything is blocking. Do NOT start any work until the owner pastes the task prompt.
2. One task prompt = one controlled change (constitution §15). Read the relevant docs and code → identify dependencies and conflicts → state what you found, what you will change, what you will NOT change, risks and tests → (in plan mode: wait for approval) → implement only the requested scope → run the tests → report with the §15 template (Changed / Files / Database / API / Security / Tests / Documentation updated / Decisions needed / Remaining issues).
3. End: run the tests of every touched package, update docs/STATUS.md (phase, last completed task id, next task id, open decisions, known issues, last test run with date and result), update every document the change affects in the same commit, and commit with a conventional message: feat|fix|test|docs|chore|refactor(scope): summary. If anything is left uncommitted or failing, say so explicitly in the report.

## Language

- Talk to the owner in Bengali. Keep technical terms, identifiers, file names, commands and code in English inside the Bengali text.
- Code, comments, documentation, commit messages, OpenAPI, tests, ADRs: English. The blueprint stays Bengali. User-facing UI text exists only as bn/en i18n keys, never hard-coded.
- Naming: RM = RPM = Regional Program Manager; Monitoring Officer = Monitoring Team; Project Officer = Project Executive. Use the English role names from the constitution §5 in code and docs.

## Working rules for Claude Code

- Scope discipline: never expand beyond the task prompt. Something else broken? Report it under "Remaining issues"; do not fix it silently.
- Ask before guessing (§2), but batch the questions: collect them, ask once, and continue with everything that does not depend on the answers.
- "Tests pass" means you executed them in this session and show the command and its summary output. Never claim untested work as done.
- Reuse first: before creating a component, hook, service, utility, query or pattern, search the repository for an existing one and extend it.
- Security first: every endpoint declares its permission name and scope; default deny; field-level protection in serializers and exports; no secrets in code, logs or commits.
- Data integrity first: no hard delete of business data; unique constraints and idempotency keys as documented; every write audited where §13 requires it.
- Git safety: never run git reset --hard, push --force, branch -D, rebase on shared history, or delete migrations. Never modify .env files that hold real secrets. Small commits per task; tag phase gates as gate-phase-N.
- Branches (the standard's model, D-167): `main` holds released code and `develop` finished work; never commit to either. A work branch `<type>/<topic>` starts from `develop` (`ae-branch.mjs start`), its pull request goes into `develop` and is squash-merged after a green CI run; a release is a pull request from `develop` into `main` on the owner's word.
- Large tasks: split into steps; finish, test and commit each step before starting the next. If the context gets long, write progress into docs/STATUS.md before continuing.
- Decisions: every new business or architectural decision is appended to docs/DECISION_LOG.md before implementation. Proposals stay "proposed" until the owner confirms in chat.

## UI rules decided by the owner (details: docs/ui/DESIGN_BRIEF.md)

- All numbers use English digits 0-9 in both languages.
- Officials work equally on desktop and phone: review, approval, lookup, profiles and dashboards must work at 360 px. Setup screens (form builder, project setup, permission panel) are desktop first.
- Calm institutional look on the asf UI system of the organization's kit (D-150, ADR-016): colours, radius and fonts come only from the asf tokens (`apps/web/src/ui/tokens.ts`: the green scale around #00A76F, Public Sans with Noto Sans Bengali), in light and dark; do not invent colours. The app's own page CSS uses the token names of `apps/web/src/styles/tokens.css`, which map onto the asf palette (docs/ui/brand/colors.md). Read the brief before any UI task.

## Stack profile

(ST-40…ST-45 of the organization's standard; one line per piece with its reason. Changing a line is a decision: DECISION_LOG first.)

- Frontend: React 19 + Vite 8 single-page PWA, React Router 8, TanStack Query 5, use-intl, Serwist (ST-01; D-073, ADR-013) — officials and volunteers on phones and desktop, offline-first (constitution §9). - Offline store tests: fake-indexeddb (dev only, D-139) — Vitest has no IndexedDB of its own.
- Backend: Node.js 24 LTS (24.16.0 or later, D-164) + Express 5 + TypeScript as ES modules (`"type": "module"`, NodeNext, relative imports ending in `.js`, `import.meta.dirname` for paths; built with `tsc` and started with `node dist/server.js`), plain modules wired by `createContainer`, `defineRoute` registry with the OpenAPI drift test (ST-02; D-074, ADR-014) — the organization's standard; the contract and audit enforcement of the constitution are kept.
- Database: PostgreSQL 17 through Prisma 7, every migration with a hand-written `down.sql` (ST-03; ADR-003; this file wins over the standard's DB-MIG-05 per constitution §9). The API's code, the seed and the scripts use Prisma only (the tagged `$queryRaw`/`$executeRaw` where a statement stays SQL, `prismaClientFor` outside the container); `pg` stays in the tests and under pg-boss (D-169), and the lint rules `apiDatabaseDriver` and `apiRawSql` refuse a `pg` import outside `src/jobs/` and the tests and the `$queryRawUnsafe`/`$executeRawUnsafe` calls.
- Authentication: own implementation of AUTH.md (Argon2id, JWT access token in memory, rotating refresh cookie, device sessions, OTP, lockout); auth-core later when its login pack and source exist (ST-04 deviation recorded in D-074 §4).
- Storage: one adapter (`apps/api/src/storage`), NAS driver (`nas`, under `STORAGE_ROOT`; tests use it on a temporary folder) and the S3 driver marked `TEMP:` until the NAS is mounted for the app (D-168), read from the standard's settings `S3_ENDPOINT` (a whole URL), `S3_REGION`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` (the earlier `MINIO_*` names are refused at start); SeaweedFS is the local S3 stand-in in development and CI only, on 127.0.0.1, with one local identity in `infra/seaweedfs/s3.json` and the bucket bootstrap `infra/seaweedfs/bootstrap.sh` (D-169); private buckets, files streamed by the API, no signed URLs (NS-30…NS-44; D-074).

- Jobs: pg-boss in PostgreSQL, separate worker process (ADR-004) — no Redis. Email: Nodemailer over the organization's SMTP (Mailpit in dev). SMS: provider-agnostic stub until a provider is chosen (O-33).
- Monorepo and tooling: pnpm 12 workspaces with `@css/*` packages (D-050; the kit's npm layout is not used), Vitest 4, Playwright, ESLint flat config, Prettier; CI on GitHub Actions (O-51). Ajv 8 with ajv-formats (dev only) validates every API test response against `docs/api/openapi.yaml` (T1.16), as `scripts/check-docs.mjs` already compiles the JSON Schemas with it.
- UI: the asf UI system of the organization's kit (D-150, ADR-016; the move is described in `docs/plans/2026-11-03-1200-migrate-asf-ui-plan.md`): `apps/web/src/ui` with the kit's `contract.ts`, `tokens.ts`, `index.ts` and `testing.tsx` and the asf template in `src/ui/templates/asf/` (MUI core 9.5 with Emotion, MUI X date pickers 9.16, Day.js, Solar icons, Public Sans and Noto Sans Bengali through `@fontsource-variable`; light and dark); the app's additions to the kit are listed in `src/ui/templates/asf/local.json` with their tests `ui.local.*.test.tsx` and pictures in `docs/ui/asf-pieces/`; pages import only `@/ui`, and a lint rule keeps MUI, Emotion and React Aria inside the template folder and refuses the earlier set `@css/ui` and Lucide (RE-UI-01 to RE-UI-05; the earlier set of D-103 and ADR-015 is removed); pages lay out with the contract's `Stack`, `Grid`, `DescriptionList` and `Text` or their own CSS on the tokens, no utility classes; the paid Minimal template only once its licence for this product is confirmed.
- Forms of the asf UI system: `react-hook-form` 7.91 with `@hookform/resolvers` 5.9 (MIT; D-150, D-169) — forms with a submit are built on the asf contract's `Form` with react-hook-form and a zod resolver (a request schema of `@css/shared` where one fits; `useSchemaResolver` and `showFailure` in `src/lib/form-schema.ts`), and the kit's confirm dialog holds its reason the same way; the dynamic application forms and the form builder's canvas and editors are their own engine; search boxes, list filters, row choices, the NID lookup and settings that save at once keep plain state.
