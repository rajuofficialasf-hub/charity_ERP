# The volunteer form refined, and the open problems of T1.9d and T1.9e fixed (T1.9f)

## Goal
The owner looked at the new volunteer form (2026-10-14) and asked for six changes and for the open problems of the last two reports to be fixed. After this task: the identity step takes the Facebook account link; the address step takes the present and the permanent address; education is its own step and profile section; the profession step holds only the profession; the full-time emergency availability is only in the skills step; there is no emergency contact; the problems of the reports are solved.

## Requirements
### The six changes
- **R1** The Facebook account is a link: it moves from the profession step to the identity step (and, in the profile, to the personal section); it must be an https link to Facebook when given: the text is parsed as a URL, the protocol is `https:`, there is no user name, password or port, the host is exactly `facebook.com`, a subdomain of it, `fb.com`, `www.fb.com` or `fb.me`, and the text has no whitespace, control character or backslash. The PWA draws the value as a link only when the same shared check passes (so an older plain id is plain text), with `target="_blank"` and `rel="noopener noreferrer nofollow"`; the server never fetches the link (no preview, no unfurl).
- **R2** The address step asks the present address (as today: the cascade to the union and the village or house line) and the permanent address (the same four levels and a line). A box "my present address is my permanent address" is ticked by default and copies the present address; the permanent address is optional and stored as given. The present address stays the one that decides the region.
- **R3** Education is its own step (after the address) and its own profile section. Its fields, all optional: the highest qualification (a list: PSC, JSC, SSC, Dakhil, HSC, Alim, diploma, bachelor, Fazil, masters, Kamil, Hafez, other), the institution name, the department or subject, the passing year (a whole number from 1950 to the current year plus 8), the result (GPA or division, at most 60 characters) and the status (studying or completed). The single education text of earlier forms is no longer asked (its data stay and show only when filled).
- **R4** The profession step holds only the profession choice and its fields; the education text, the earlier projects and the Facebook id are gone from it. The earlier-projects text is not asked any more anywhere (its data stay and show only when filled).
- **R5** "Can you give full time in an emergency?" is a yes or no in the skills group only; it leaves the job seeker's profession fields.
- **R6** There is no emergency contact: not in the form, the profile, the approver's views, the API, the field class or the logs; its two columns are dropped by a migration (the data were entered for tests only; nothing has been released).

### The open problems
- **R7** The API answers that carry personal data (the own profile, the registration an approver opens, the edit and correction requests, the files already have it) say `Cache-Control: no-store`.
- **R8** The PWA empties its cache of server data when the signed-in user's permission version changes, so an approver who lost a field class does not keep the values on screen.
- **R9** Leaving a section in the edit mode with ticked details asks first ("leave and drop what you ticked?").
- **R10** A staff registration approved with a role of GLOBAL scope (Monitoring Team) makes the person set a new password at the next sign-in: the account is flagged, every operation but `auth.me.get`, `auth.password.change`, `auth.me.language.set` and `auth.session.logout` answers 403 `auth.password_change_required` while it is flagged (the sign-in, the refresh and the password reset are public routes and keep working), the PWA opens the password screen with a short notice, and a completed password change or password reset (12 characters for a global role, O-25, derived on the server from the roles; the new password may not equal the current one) clears the flag at once, also for the cached session facts.


The logout and stale-token fix of the earlier session is delivered by the merge `57d6152`; it has no unit.

## Scope
- In: the shared schemas and lists, one migration, Prisma, the volunteer submit, the profile and detail views, the edit and correction fields and their apply step, the field class entry, the registration steps (eight now), the profile sections, the approver's views, the catalogue texts in both languages, OpenAPI, DATABASE_SCHEMA, SCREENS, STATUS, tests and e2e; the no-store header, the cache clearing, the leave warning, the forced password change.
- Out: the staff registration form; a configurable list of qualifications; forcing a change for existing global accounts (only a new approval flags); exports; the Hijri or other calendar of a date.

## Key decisions
- **O-66** (owner, 2026-10-14): the six changes of the message and its answers: the permanent address is optional with a "same as present" box; the earlier projects leave the form; the full education set; a global role makes the person change the password at the next sign-in. "Fix the problems" is the approval of R7 to R11.
- **D-093** (implements O-66): the Facebook link keeps the column and the field name `facebookId` (it holds the link; the new rule validates it); `volunteers.education_details` (JSONB object, a strict schema), `volunteers.permanent_address` (JSONB object or null, the four location ids and a line, checked with `addressProblem`), `volunteers.emergency_full_time` (boolean) are added and `emergency_contact_name` and `emergency_contact_mobile` are dropped (migration `20261014120000_volunteer_education_permanent_address`, reversible); `users.password_change_required` (boolean) with a flag on `Me`; the access middleware refuses a flagged account except for the operations marked `allowPasswordChange`; the edit and correction fields get `educationDetails` and `permanentAddress` (groups) and lose `emergencyContact`; `skills` gains `emergencyFullTime`.
- Reuse: `ProfileInputs`, `ValueEditor`, `EditSection`, `AddressFields`, `AddressNames`, `ProfessionText` (T1.9e), `applyField`, `OBJECT_FIELDS`, the field mask, `ConfirmDialog` of `packages/ui`.

## Risks and rollback
- **Migrations:** one adds columns and drops two columns that held test data only (its down.sql adds them back empty); one adds a boolean with a default. Both are reversible and tested by the round trip.
- **Contract:** the submit refuses `education` and `emergencyContact` and takes `educationDetails` and `permanentAddress`; a job seeker's `fullTimeAvailable` moves to the skills; the web and the API are deployed together.
- **Auth:** a flagged account is locked to four routes until the password changes; a mistake would lock the new Monitoring Team member out, so the test covers the allowed routes and the clearing; only an approval after this release flags an account.
- **Personal data:** the blood group and the date of birth stay in `volunteer.identity`; the permanent address is not protected (like the present one).
