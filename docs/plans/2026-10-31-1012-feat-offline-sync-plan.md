# Offline PWA and sync (T2.7)

## Goal
A volunteer whose phone has no network opens the installed app, takes new beneficiary applications with their photos, edits drafts and sends them to the office; when the network returns the app sends everything by itself, shows what is still waiting and what failed and why, and nothing is lost. The office sees a record that came through sync exactly as one made online. What the phone keeps is encrypted and disappears at logout or when an official revokes the device.

## Problem
Field work happens on 2G/3G and in places with no signal at all (blueprint B7, NFR-12 to 19). Today every save of the application form is a live API call, the answers live only in the open tab, the service worker caches nothing but the build, and the two sync endpoints exist only in `openapi.yaml`. Without this task the Phase 2 gate's offline scenarios and the Phase 3 pilot cannot start (D-134). The design is done (`docs/architecture/OFFLINE_SYNC.md`, O-07, O-13, O-29, BD-48); this task builds it, with the owner's answers of 2026-10-31 below where the design left a gap or a choice.

## Requirements

### A. The installable app and its shell
- **R1** The app installs from Android Chrome and from iOS Safari ("Add to Home Screen"), opens standalone with the brand icon and name, and shows an in-app install hint in Bangla and English: a one-tap install button where the browser offers it, and the three-step iOS instructions where it does not; the hint can be dismissed and comes back from the account menu.
- **R2** With no network, every signed-in screen of the app shell opens from the cache, with the self-hosted fonts (UbuntuSans and Bornomala), the icons and both language catalogues; no page asks the network to render its frame.
- **R3** A new build of the app never breaks an outbox that is waiting: the new service worker takes over only when the open tabs allow it, and a record written by the old build still syncs under the new one.

### B. What the phone keeps for a volunteer (O-07, NFR-21)
- **R4** After a sign-in with network the phone holds, for the signed-in volunteer: the assigned projects they have consented to (name, state, deadline, limits, photo rule and source, rules text, the consent state), the published application form version of each, the volunteer's own applications (state, stage, the person's name, father or husband name, village, the volunteer-visible answers), the locations master (division to union, active rows) and the reference lists the forms need; a team member also holds the lead's team membership state.
- **R5** The phone never holds an NID or birth-registration number, an NID photo, bank details, ratings, categories, scores or any official-only section; the snapshot applies the same field mask as every other read (BR-183). The only identity number on the phone is the one the volunteer typed into a not-yet-synced record, inside the encrypted outbox.
- **R6** The data set refreshes on every sync by deltas (`since`, `ETag`): a project the volunteer is no longer assigned to, or one that closed, disappears from the phone together with its form; a project's consent revoked by a rules change removes the project's "new application" entry until the volunteer consents again online.
- **R7** The dawah syllabus of O-07 is not part of this task: the dawah module (Phase 5) does not exist yet, so there is nothing to cache; the snapshot gains it with that module.

### C. Offline writes: the outbox (BR-194, BR-195)
- **R8** Without network a volunteer, or a team member for their lead, can start a new application in an assigned project from the cached form: type the identity number and the basic fields by hand (no lookup, no auto-fill, a short notice says why), fill every part with the same renderer, logic, calculations and validation as online (BR-076), attach photos, save the draft, and send it to the office; the screen says "saved on this phone, will be sent when there is network" and gives no application number yet.
- **R9** Without network a volunteer can open and edit any own draft the phone holds (one made offline or one pulled from the server), and fill an answer the office opened for correction (the unlock of T2.6); the edit joins the outbox.
- **R10** Every offline write is one outbox record with a client id (`client_uuid`), its kind (`application_draft`, `application_submit`, `application_update`, `field_update`), the project and the form version, the device's creation and update times, and its dependencies (a submit waits for its draft); the record carries the clock offset learned at the last sync so the server can judge the creation time (O-13).
- **R11** Online, the same path is used with an immediate flush: there is one code path for saving an application, not an online and an offline one; a save that fails on the network simply stays in the outbox.
- **R12** A record moves pending → syncing → synced, or → failed with a reason the volunteer can read in Bangla; a failed record can be edited and sent again (a new version under the same client id) or, for a draft, deleted; a `needs_verification` result counts as synced and is shown as "the office is checking this".
- **R13** A synced record is purged from the phone 7 days after the server confirmed it and no photo or dependant of it is still pending (O-29).

### D. The sync engine (OFFLINE_SYNC §3, §4)
- **R14** The outbox flushes on app open, on the `online` event, when the app returns to the foreground, after any local write while online, on "sync now", and every 15 minutes while open and online; text records flush before any photo upload (BR-196).
- **R15** Records go to `POST /sync/batch` in creation order with dependencies respected, at most 50 records and at most 1 MB per batch under one `Idempotency-Key`; each record answers on its own (synced, needs_verification, failed with a code); the batch never fails as a whole because one record failed; a replayed batch returns the stored results, a replayed record never creates a duplicate.
- **R16** Each record is processed on the server by the ordinary application service with the volunteer as actor, so permission, scope, guards, effects, notices and audit are identical to the online path; the server records the batch under the device session.
- **R17** Transient failures (network, timeout, 429, 5xx, 503) retry after 30 s, 2 min, 10 min, 1 h, then hourly for 7 days with ±20 % jitter, honouring `Retry-After`; after 7 days the record stays failed with `retry_exhausted`; permanent refusals (validation, guard, permission, other 4xx) never retry by themselves (BR-236).
- **R18** Every flush starts by refreshing an expired access token; a refresh that fails as expired keeps the outbox and asks the volunteer to sign in; a revoked session wipes the phone (R33).
- **R19** The snapshot of section B is pulled after each successful flush and on app open while online, at most once per 15 minutes unless the volunteer asks.

### E. The photo queue (BR-196, BR-237, NFR-25)
- **R20** A photo attached offline is compressed on the phone (JPEG, at most 1,600 px on the long side, aiming at 300 KB), stored with its capture time, position and source in a separate queue keyed by the record's client id and the answer slot, and never travels inside a record batch.
- **R21** A photo uploads only after its record is synced and has a server id, through the chunked, resumable upload of T2.1 (256 KB parts, resume from the parts the server holds after a drop); the answer on the server is completed with the file id when the upload finishes.
- **R22** The queue has a budget of 200 MB on Android and 100 MB on iOS: at 80 % the app warns and suggests syncing; at 100 % new photos are refused with a message and a "free space" action that deletes only photos whose server copy is confirmed; a not-yet-uploaded photo is never deleted by itself.
- **R23** The application's list row and detail show "photos pending" while any photo of a synced record is still in the queue; the office sees the application without those photos until they arrive and the record carries the pending count.

### F. The server's rules at sync (BD-48, O-13, BR-104, BR-199)
- **R24** An offline record whose identity number already belongs to a profile is linked to that profile when the typed name and father or husband name match the profile's (after trimming, case and Bengali-Latin digit normalisation, ignoring punctuation and double spaces), exactly as an online creation links; the typed identity answers are then replaced by the profile's locked values. When they do not match, the application is created in `needs_verification` with the typed values kept, the existing profile named as the candidate, and the office resolves it with the verify dialog of T2.6 (link or create). Owner's choice of 2026-10-31; it amends the wording of BR-104.
- **R25** A record on an approved application's locked field, or any locked data, is refused with `locked_on_server` and the server's value; the client shows it and discards the local change; the attempt is audited as `sync.conflict_server_won` with both values.
- **R26** A draft or pending application edited both on the phone and on the server follows last write wins by the offset-corrected update time; the losing version goes into the audit entry `sync.conflict_last_write`.
- **R27** A record created before the project's deadline but synced after it is accepted and flagged `needs_verification` with `deadline_passed_in_sync`; one created after the deadline is refused with `deadline_passed`; a submit that would exceed the volunteer's limit at sync time is refused with `limit_exceeded`; a record on a closed project is refused with `project_closed`; a blocked volunteer's or a removed assignment's record is refused with `not_permitted` and stays on the phone until deleted.
- **R28** A record on a form version republished meanwhile is accepted under the old version when its creation time precedes the new version's publish time; one created on the stale cached form after that is accepted under the old version and flagged `needs_verification` with `stale_form_version`; the phone keeps the old version until no draft references it and the form screen says "the form was updated; syncing refreshes it".
- **R29** Every result code the server returns has a Bangla and English message that tells the volunteer what to do (`sync.*` and the existing `application.*` codes).
- **R30** The office's review page and the application timeline show that a record arrived through sync, its device creation time and, for a flagged one, the verification reason; the attention list of the home counts the office's new `needs_verification` items as it does today.

### G. What protects the data on the phone (BR-198, BR-238, O-29 item 5)
- **R31** Every table that holds business data (outbox, photo queue, cached applications, cached forms with answers) is encrypted field by field with AES-GCM; locations, reference lists and the language catalogues are not.
- **R32** The data key is wrapped twice: under a device key the server issues (at login the server creates a random 256-bit key for the device session and returns it in the response body, never a cookie; the app keeps it in memory only; each refresh returns it again; the server stores it sealed with the device session), and under a device-bound key the browser holds as a non-extractable `CryptoKey` in IndexedDB, so the app opened without network after a cold start can still read and write its tables. The wrapped data key, never the device key or the data key, is written to the phone. Owner's choices of 2026-10-31 (brainstorm, then the plan review for the offline cold start), replacing the refresh-token derivation of OFFLINE_SYNC §7, which the app cannot perform because the refresh token is an HttpOnly cookie; this is the "platform-appropriate device-bound key" of O-29 item 5.
- **R33** When the session expires (`auth.refresh_invalid`), the encrypted outbox and queue stay on the phone; after a new login on the same device the server returns the device key of the previous session of that device when the app presents the device's stored session id and the login succeeds for the same user, the data key is unwrapped and re-wrapped under the new key, and sync continues; nothing is silently discarded. When the previous device record is gone (revoked, deleted, another user) the app reports how many records it could not recover, audits `sync.outbox_unrecoverable` with the count, and then wipes the unreadable tables; a different user signing in on the phone sees only a generic notice, never the count or the owner of the leftover data.
- **R34** Logout wipes the outbox, the queue, the cached data, the service-worker API caches and the keys; a logout while records are pending shows a blocking warning with the counts and "sync now", needs a second confirmation, and is logged at the next login (`auth.logout_with_pending`, count only). A device revoked by an official (`auth.session_revoked`) or a reused refresh token wipes everything at the next request; the official's confirm dialog of the sessions screen shows the device's pending count.
- **R35** The app requests persistent storage (`navigator.storage.persist()`) at the first login and shows, on iOS, the notice that unsynced work is lost if the app is removed or Safari data is cleared.

### H. What the volunteer sees (OFFLINE_SYNC §9, SCR-005, UX-12)
- **R36** An offline banner at the top of every screen when the device reports offline or the last request failed on the network: "আপনি অফলাইনে আছেন। আপনার কাজ এই ফোনে জমা আছে।" with the pending count; it disappears when a request succeeds.
- **R37** A sync chip in the app bar with the pending and failed counts; a tap opens the sync centre at `/sync` (phone-first): records grouped by state with the Bangla reason of each failure, "আবার পাঠান" per record and for all, "সম্পাদনা" and "মুছুন" for drafts, the photo section with uploaded and pending bytes and the budget bar, the last successful sync time, and the iOS notice; an empty state when everything is synced.
- **R38** Per-record badges on the volunteer's application list and detail: pending, syncing, failed, needs verification, photos pending.
- **R39** The "needs your attention" widget of the volunteer home lists failed records, records the office is verifying and photos pending, each opening its record or the sync centre (`ATTENTION_ROUTES` gains the kinds).
- **R40** A reminder appears when a record has been pending for 24 hours and once a day after that while anything is pending, as an in-app notice on the device (no server message); it stops when sync succeeds.
- **R41** Every message uses i18n keys and English digits (UX-05); every new screen works at 360 px and passes the axe sweep in both languages.

### I. Background sync
- **R42** Where the browser offers the Background Sync API (Android Chrome) the service worker registers a one-shot sync when the outbox is not empty, so a flush runs when connectivity returns even with the app closed; everywhere else, and always on iOS, the foreground triggers of R14 are the whole mechanism and the UI never promises a sync "later by itself".

### J. Officials
- **R43** An official's installed app opens offline to the shell and the cached home with the banner; the review, approval, lists and lookups say they need a connection. No official data set is cached and no official write is queued in this task. Owner's choice of 2026-10-31.

### K. Proof
- **R44** Unit tests cover the outbox state machine (states, retries with jitter and `Retry-After`, dependencies, purge), the conflict rules, the clock offset, the form-version selection, the name match of R24, the photo budget and the key wrap/unwrap.
- **R45** API tests cover `POST /sync/batch` (batch and record idempotency, per-record results, needs-verification routing, link-on-match, deadline, limit, closed project, blocked volunteer, locked field with its audit, stale form version, payload limits, another user's record refused) and `GET /sync/snapshot` (deltas, removals, the field mask, 304).
- **R46** Playwright, on the mobile project with offline emulation and a throttled 3G profile: capture an application with a photo offline → reconnect → it syncs, the photo follows, the list shows the number; an offline application whose NID exists with another name → "the office is checking this" and the office resolves it; a draft edited on both sides; logout with pending records shows the warning; a revoked device wipes the phone; the photo upload resumes after a drop.
- **R47** A manual checklist for the owner, in Bangla, for an installed app on an Android phone (Chrome) and on an iPhone (Safari tab and installed): install, offline capture, reconnect, persist() prompt, the iOS notice, logout wipe; the results are recorded in `docs/testing/` before the Phase 2 gate. Claude cannot run on a real phone; the owner runs this list and reports.

## Key decisions
- **Offline writes are the application's work only** (new draft, draft edit, send to office, photos, the unlock answer): the field's core job; everything else a volunteer writes stays online with a plain message. Owner, 2026-10-31. Governs R8, R9, Scope.
- **Volunteers only in this task**: officials get the installable shell and the banner, no cached queues or offline decisions, which would need a new rule for two officials deciding the same application. Owner, 2026-10-31. Governs R43.
- **An existing identity links when the names match, otherwise needs verification**: the online path already links a known number; the only offline difference is the hand-typed name, so a match links and a mismatch goes to the office. Owner, 2026-10-31; amends the wording of BR-104 and keeps BD-48's "never rejected". Governs R24.
- **A server-issued device key and a device-bound browser key both wrap the data key**: the refresh token is an HttpOnly cookie the app cannot read, so OFFLINE_SYNC §7's derivation is impossible. The server's key, kept only in memory on the phone, lets a session that merely expired recover its outbox after re-login on the same device and dies with a revocation (O-29 item 5); the browser's non-extractable key lets the app open offline after a cold start, which a memory-only key cannot (found in the plan review). The protection is the phone's lock screen and the browser's private storage; a copied storage of a rooted phone could open the data, which the owner accepted against the PIN and online-session-only alternatives. Owner, 2026-10-31 (brainstorm and plan review). Governs R31 to R33.
- **No mockup first**: SCR-005 is specified and the other pieces are small; the owner reviews in the built app. Owner, 2026-10-31.
- **O-29's values stay constants** in `@css/shared/sync` (retry ladder, 50 records and 1 MB per batch, 256 KB parts, budgets, 7-day purge, 24-hour reminder); changing one is a decision, not a setting. Confirms the 1 MB PROPOSAL of OFFLINE_SYNC §15.
- **One save path for online and offline** (R11), so a network drop in the middle of a form never changes what the volunteer does.
- **Decision record**: these answers are appended to `docs/DECISION_LOG.md` as D-139 before implementation (constitution §2); the rule rows BR-104, BR-194 to BR-199, BR-236 to BR-238 move from deferred to tested as the units land.

## Technical decisions
- **Stack profile** (`ST-40`, `ST-43`): the profile of `CLAUDE.md` stays (React 19 + Vite PWA with Serwist, Express 5, Prisma 7, the storage adapter). This task adds one runtime piece, **Dexie 4** (Apache-2.0) for the IndexedDB tables, named by the constitution §9 and D-052 as the outbox store, because raw IndexedDB needs hundreds of lines of request plumbing that Dexie replaces and typed, versioned schemas are needed for the encrypted tables (`ST-30`: checked, no stack piece covers client storage). Dev only: **fake-indexeddb** for Vitest. U1 writes both into the `CLAUDE.md` stack profile with their reasons and D-139 records them. Nothing else is added: encryption uses WebCrypto, the service worker stays Serwist 9.5.13, uploads reuse `apps/web/src/lib/uploads.ts`.
- **One save path** (R11): the application screens call a store (`apps/web/src/offline/applications-store.ts`) that writes an outbox record and asks the engine to flush; online the flush runs at once and the screen reads the result; offline the record waits. The screens never call `createApplication`/`updateApplication`/`actOn` directly any more. This follows the existing pattern of `lib/uploads.ts` (one function, retries inside) rather than a second offline branch in each screen.
- **The server processes sync records through `ApplicationsService`** (ADR-010, SYSTEM_ARCHITECTURE §6 step 11): a new `SyncService` maps each record kind to `create`, `update`, `actOn('submit')` or `UnlocksService.fill`, each record in its own transaction (the service methods open theirs), so a refused or crashing record rolls back alone and the batch never fails as a whole. The batch key is handled by a new mode of `IdempotencyService` next to `runWithKey` (`apps/api/src/idempotency/idempotency.service.ts:41-88`): `reserveKey` inserts the `sync_batches` row with `results: null` first (a replay with stored results answers them; a replay while results are null answers 409 `sync.batch_in_progress` with `Retry-After`; a different body under the same key or a key of another user answers 422 as today), then `storeResults` writes them when every record is done. The `clientUuid` lookup, the stored batch and every record's target are scoped to the actor: `earlier` (`applications/service.ts:832-859`) already answers 404 for a record that is not the caller's own, `ownerFor` (`:898`) re-checks a team member's lead and membership on every record, and `SyncService` never reads an owner from the client. The sync-only rules (late sync, stale version, name match, conflicts) are options the service passes (`via: 'sync'`), never a second implementation of the guards. The result codes are `ApiError` codes rendered by `src/http/errors.ts` as today.
- **Flags, not new states**: the application `flags` check constraint already allows `late_sync`, `stale_form_version` and `existing_identity` (migrations `20261011000000_init`, `20261021160000_application_public_flags`), and `needs_verification` intake exists in `services/public-forms.ts:76-169` with the verify actions in `applications/service.ts:1150-1200`. The sync path writes the same status and flags, so the office resolves offline records with the T2.6 verify dialog unchanged. R27's reason reads `late_sync` in the result and the flag; the message says the deadline passed during sync.
- **Name match for R24** lives in `@css/shared/sync` as a pure function (`namesMatch`) over `normalizeText` of `@css/shared/i18n` plus digit normalisation (`toEnglishDigits`), punctuation and whitespace folding, applied to the name and the father or husband name, and runs only for records that arrive through sync (an online creation has the profile's values auto-filled, so it links on the number as today, `applications/service.ts:929-989`).
- **Clock offset** (O-13): the batch carries `deviceTime`; the server computes `offset = serverNow - deviceTime` and stores `clientCreatedAt` corrected by it on the application (the existing column); `clientUpdatedAt`, corrected the same way, is compared with the application's `updatedAt` for R26. The client keeps the last offset from `serverTime` for display only.
- **Last write wins on drafts** (R26): the sync record carries `baseVersion` (the ETag the edit started from). Same version: an ordinary update. Different: the later of the corrected `clientUpdatedAt` and the server's `updatedAt` wins; a client win applies the answers and audits `sync.conflict_last_write` with the server's answers as `old`; a server win answers `synced` with `conflict: { kept: 'server' }` and the same audit, and the client replaces its copy from the next snapshot. A locked application (R25) answers `failed` with `locked_on_server` and `conflict: { serverValue }`, audited `sync.conflict_server_won`. `conflict.serverValue` passes the same field mask as every read (`access/field-mask.ts`): a locked field the volunteer may not see (the identity number, the official section) answers `locked_on_server` with no value. The audit entries hold both answer sets as `application.update` audits already do, readable only through the audit viewer of the global roles (T1.13). `RowResult` gains the optional `conflict` object in `openapi.yaml` (the schema was declared, not built, so this is an adjustment, not a breaking change).
- **Pending photos** (R20, R21, R23): an answer of a file field made offline is sent as a placeholder `{ pendingPhoto: true, slot }`; the server validates it as present, stores `null`, keeps the slot in the application's `pendingPhotos` list (a JSONB column added by migration, nullable, default empty array) and answers `pending_photos` in the result; `UploadsService.finalize` (`apps/api/src/services/uploads.ts:215`) fills the answer and removes the slot when a file arrives for `entityType: 'application'` with that slot, through a hook `ApplicationsService.attachPendingPhoto`, which re-checks that the uploader owns the application (or is a team member of its lead), that the application is still editable by its owner or waiting in `needs_verification` (otherwise `locked_on_server`), that the slot is listed, and that the file's source matches the project's photo source rule; the client's capture time and position are stored as metadata and flagged exactly as online uploads are (BR-109, `files/flags.ts`). The form's required check treats a slot listed in `pendingPhotos` as answered, so a submit with a pending required photo goes through; review and approval proceed with the visible "photos pending" flag, because BR-196 gates only photo-gated completion steps (distribution, Phase 3). The record's read view exposes `pendingPhotos.length`.
- **Snapshot** (R4 to R6): `GET /sync/snapshot?since=` answers `{ serverTime, projects, formVersions, applications, applicationIds, locationsVersion }` by composing the existing services (`MyProjectsService` for the consented projects, `FormsService`'s volunteer-audience definition as `GET /projects/:id/application-form` answers it, `ApplicationsService.listOwn` for changed rows) with the field mask of every read. `applicationIds` is the full id list of the caller's own applications, so the client deletes what it holds and the server no longer lists (replaces the declared `removedIds`, which would need the server to know the client's state); `beneficiaries` is dropped from the declared schema because the person's allowed fields travel inside each application. Locations come from a new `GET /locations/all` with an `ETag` (about 5,000 rows, cached in Dexie unencrypted).
- **The keys** (R32, R33): `device_sessions.local_key` (bytea, nullable; migration with `down.sql`) holds 32 random bytes sealed with AES-256-GCM under a key derived (HKDF) from the server secret `LOCAL_KEY_SECRET`, with the session id as associated data so a sealed value cannot be moved to another row (`NE-CFG-01`; a local default is refused in production per `NE-CFG-04`; listed in `.env.example`; rotating the secret re-seals every live row through a script, documented in the runbook). The column is nulled on logout and on revocation, and a nightly job nulls it 30 days after a session's expiry, which bounds the recovery window. `TokenPair` gains `deviceKey` (base64url), returned by login and refresh (`services/auth.ts:222-257`) and never logged (`NE-LOG-02` redact list). `loginRequestSchema` gains optional `recoverSessionId` and `lostPending: { count, reason: 'logout' | 'unrecoverable' }`: when the named session belongs to the same user, is expired but not revoked, and still holds a key, the login answers `previousDeviceKey` once and clears the old column; otherwise it audits `sync.outbox_unrecoverable` with the count; a `lostPending` with reason `logout` audits `auth.logout_with_pending`. `POST /auth/logout` takes an optional `pendingCount` for the online logout. The batch request carries `pendingAfter` (the records left on the device after that batch), stored as `device_sessions.pending_count` and `pending_reported_at`, so the sessions screens can show what a device still holds. On the phone the data key is generated extractable once per install, its raw bytes are wrapped (AES-GCM) under the device key and separately under a device-bound AES-GCM `CryptoKey` generated non-extractable and stored in Dexie as a `CryptoKey` object (the browser keeps it in its own storage), then the data key is re-imported non-extractable for use; the two wrapped blobs sit in the `keys` table with the session id; the device key itself lives only in module memory. Recovery unwraps the raw bytes into an extractable key, re-wraps under the new device key and re-imports. Revocation (`auth.session_revoked`) and logout wipe everything through `lib/wipe.ts`, whose `css-*` IndexedDB rule already covers the new databases.
- **Offline cold start** (R2, R8, R9, R18): the app opened without network after the process was killed has no access token and no device key; it treats a volunteer with a `keys` row whose device-bound key unwraps the data key as signed in offline (the cached `me` of the last snapshot gives the roles), reads and writes its tables, and shows the banner; the first flush after the network returns starts with a refresh, which brings the device key back. A refresh that fails on the network (not as expired) is transient: the outbox stays pending and the retry ladder applies.
- **Encrypted photo bytes** (R31): a queued photo is stored as AES-GCM ciphertext of its `ArrayBuffer` with a per-row IV and the capture metadata inside the encrypted JSON; a preview is an object URL made from the decrypted bytes in memory and revoked when the field unmounts; nothing goes into the Cache API. Encrypting 300 KB with WebCrypto takes a few milliseconds on a 2 GB phone.
- **Background sync** (R42, limit): the service worker registers a one-shot `sync` when the outbox is not empty; on the event it posts `flush` to an open window client, which holds the keys and tokens; with no client open the service worker cannot decrypt the outbox (the key is memory-only by R32) and does nothing, so the flush runs at the next open.
