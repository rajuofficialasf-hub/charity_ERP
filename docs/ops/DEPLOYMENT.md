# DEPLOYMENT

Status: outline, written in task T0.1 (2026-10-10); completed in task T3.0 (pipeline, staging, backup before the pilot) and finalized in task T6.5 (production hardening). D-053 approved (O-01); backup targets decided (O-06: RPO 24 h then 1 h with WAL, RTO 4 h, monthly drill); server details still to be supplied by the owner.

## 1. Environments
Development (Docker Compose), test (CI), staging and production on the organization's server; configuration and secrets per environment.

Development (ORG-DEV-01, T1.7d): `docker compose up` from the repository root runs the whole ERP — `infra/docker-compose.dev.yml` (PostgreSQL 17, SeaweedFS as the local S3 stand-in, Mailpit) plus `infra/docker-compose.app.yml` (one-shot `setup` and `migrate`, then `api` and `web` from the development image `docker/app/Dockerfile.dev`, the repository bind-mounted, dependencies in volumes, dev-only placeholder secrets, dummy OTP). Nothing of it is used beyond a developer's machine: staging and production get their own compose project, images and secrets (T3.0).

## 2. Topology
Reverse proxy with TLS, API, web, workers, PostgreSQL, object storage, mail relay; ports and networks.

Web (D-073, ADR-013): the PWA is static files (`apps/web/dist` from `pnpm --filter @css/web build`); Caddy serves them with the SPA fallback (every unknown path returns `index.html`), long cache headers for `assets/*` (content-hashed) and no cache for `index.html`, `sw.js` and `manifest.webmanifest`, and routes `/api/v1/*` to the API on the same origin (the refresh cookie and CSRF need it, AUTH.md 5). No Node process runs for the web app. The API's `TRUST_PROXY` names Caddy's address (D-072). Caddy's access log records paths without query strings, because list searches carry names, mobile numbers and NIDs in the query (O-67). Written in full in T3.0.

## 3. Build and release
Build steps, versioning, release checklist, database migrations with `down.sql`, zero-downtime considerations.

## 4. Configuration
Environment variables (names only, never values), SMTP and SMS provider settings, dummy OTP disabled in production (BR-024).

API and worker variables (T1.6; schema in `apps/api/src/config/env.ts`): `NODE_ENV`, `PORT`, `SHUTDOWN_DELAY_MS` (default 0, at most 5000; how long the API keeps serving after SIGTERM once readiness answers 503, set to the proxy's readiness poll interval when one polls; the container's `stop_grace_period` must exceed 35 seconds plus this), `DATABASE_URL`, `LOG_LEVEL`, `CURSOR_SECRET`, `JOBS_INLINE` (must be false in production), `STORAGE_DRIVER` (no default; `nas` = the organization's NAS mounted at `STORAGE_ROOT`, `s3` = an S3 store through the S3 API until the NAS is mounted, D-074, D-168), with `s3` `S3_ENDPOINT` (required; the store's whole URL `scheme://host[:port]` without a path, https outside a private network), `S3_REGION` (default `us-east-1`, which a self-hosted store accepts), `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY` (both required), `STORAGE_ROOT` (the NAS mount, an absolute path the api and the worker can read and write; required with `nas`), `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMS_MODE`; since T1.7 `JWT_SECRET`, `JWT_PREVIOUS_SECRET` (only during a key rotation), `AUTH_CSRF_SECRET`, `OTP_SECRET` (each a random value of at least 32 characters, different per environment), `OTP_DUMMY_ENABLED` (must be false in production), `OTP_DUMMY_CODE` (development and test only), `AUTH_COOKIE_SECURE` (must be true in production), with the rule that a production start refuses every local example secret (a value starting `change-me` or `dev-only-` or containing `css_dev_only`) in `JWT_SECRET`, `JWT_PREVIOUS_SECRET`, `AUTH_CSRF_SECRET`, `OTP_SECRET`, `CURSOR_SECRET`, `LOCAL_KEY_SECRET`, `LOCAL_KEY_PREVIOUS_SECRET`, `SMTP_PASSWORD`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and the password of `DATABASE_URL`, naming the key and never the value (D-167), `ALLOWED_ORIGINS` (other browser origins allowed to call the API with credentials, comma separated, each an exact `scheme://host[:port]`; production takes only https on a real host; empty when the PWA and the API share the origin behind Caddy), `TRUST_PROXY` (Caddy's address or network so the API sees the user's address, D-072; default `loopback`; the rate limits and the public link's photo share per sender key on that address, so a wrong value makes every applicant one sender, D-179), `RATE_LIMITS_RELAXED` (E2E only, refused in production), `SESSION_DEVICE_LIMIT_RELAXED` (E2E only, the device limit a hundredfold because the specs share the demo accounts; refused in production, D-102); since T1.8 `PERMISSIONS_FILE` (optional path of `permissions.yaml`; by default the API and the worker read `docs/security/permissions.yaml` relative to their build, so the T3.0 images must contain that file; both refuse to start when it is missing or invalid). Since T1.13 `SMS_API_KEY` (optional; the SMS provider's key once one is chosen, O-33; the channels page shows only whether it is set) and `APP_VERSION` (the release shown on the system health page; set it per deployment). Since T2.7 `LOCAL_KEY_SECRET` (a random value of at least 32 characters, different per environment; seals the device keys of sessions in the database, AUTH.md §5; production refuses the example value) and `LOCAL_KEY_PREVIOUS_SECRET` (only during a rotation). Since T2.1 `FILE_SCANNER` (the virus scanner of uploaded files; `skip` exists for development and test only and production refuses it, so the first deployment adds the organization's scanner, ClamAV on its own server by default, D-109; a staging server that holds real data runs the real scanner too, since `skip` lets unscanned files be viewed outside production). The worker processes uploaded files on the `photos` queue (scan, photo metadata, thumbnails, near duplicates) with sharp, whose prebuilt binary for linux-x64 glibc comes with `pnpm install` on the image. Start-up order: the storage buckets (every bucket of FILES_AND_DOCUMENTS §8, private, incl. `uploads`, as `infra/seaweedfs/bootstrap.sh` creates them in development; a production S3 store also keeps the versioning of `documents` and `photos` and the expiry of `exports` and `uploads` that the development store leaves out; the readiness probe fails while one is missing), `pnpm db:migrate` (Prisma migrations, then the pg-boss schema and queues, D-069, then the missing notification templates, then the missing roles and permissions of `docs/security/permissions.yaml`, workflow templates of `docs/architecture/workflow-templates/` and base reference lists with `reference:sync`, D-179), then the api (`node dist/server.js`) and the worker (`node dist/worker.js`).

Exports (T2.8, D-143, D-144): the worker consumes the `exports` queue and runs the daily export sweep at 03:30 Dhaka time. The PDFs are printed by the Chromium of `playwright-core` inside its sandbox, which the owner approved for the worker host (D-144). On the worker host, as root:

1. Run the worker as its own non-root user (for example `css-erp`); Chromium refuses its sandbox to root.
2. Install Chromium where the profile expects it: `PLAYWRIGHT_BROWSERS_PATH=/opt/css-erp/ms-playwright pnpm --filter @css/api exec playwright-core install --with-deps chromium` (about 170 MB), and give the worker the same `PLAYWRIGHT_BROWSERS_PATH` in its environment.
3. On Ubuntu 23.10 or later, open user namespaces to Chromium alone: `cp infra/apparmor/css-erp-chromium /etc/apparmor.d/css-erp-chromium` and `apparmor_parser -r /etc/apparmor.d/css-erp-chromium`. Leave `kernel.apparmor_restrict_unprivileged_userns` at 1; the host-wide switch is for the throwaway CI runners only.
4. A worker in a container keeps Docker's user namespaces closed unless it runs with Chromium's seccomp profile (`--security-opt seccomp=<profile>`); never `--privileged`, and never `--no-sandbox`.
5. Check it as the worker user, from `apps/api`: `node -e "require('playwright-core').chromium.launch({ chromiumSandbox: true }).then((b) => b.close()).then(() => console.log('sandbox ok'))"` prints `sandbox ok`.

The PDFs embed Public Sans and Noto Sans Bengali, read from the API's own dependencies `@fontsource-variable/public-sans` and `@fontsource-variable/noto-sans-bengali` (`apps/api/src/exports/pdf/fonts.ts`), so the worker's image needs the API's installed production dependencies (until D-150 the fonts came from `packages/ui/fonts/`). Without the sandbox or the fonts, PDF jobs fail with `export.pdf_unavailable` while Excel and CSV keep working. Plan about 1 GB of memory for the worker with one large Excel export running (docs/testing/PERFORMANCE.md, "Exports").

## 5. Deployment procedure
Step-by-step deploy and rollback; smoke tests after deploy.

Deploy note, the S3 settings' names (D-169): the API reads the store of `STORAGE_DRIVER=s3` from `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID` and `S3_SECRET_ACCESS_KEY`. The earlier names are refused at start, each naming the one to set, so a configuration that still carries one never starts without a store: `MINIO_ENDPOINT`, `MINIO_PORT` and `MINIO_USE_SSL` become the one URL `S3_ENDPOINT` (for example `https://s3.internal.example.org:9000`), `MINIO_ACCESS_KEY` becomes `S3_ACCESS_KEY_ID` and `MINIO_SECRET_KEY` becomes `S3_SECRET_ACCESS_KEY`. No environment was deployed before the rename; a developer's `apps/api/.env` takes the `S3_*` lines of `apps/api/.env.example`.

Deploy note, the list of whose number a mobile is (D-172): migration `20261112160000_beneficiary_optional_identity` adds `beneficiaries.mobile_owner_code`, whose codes come from the reference list `mobile_owner` of the base seed and not from the migration. After `pnpm db:migrate`, the base seed (`pnpm db:seed --set base`) must run before the "whose number" question is used; until then every code is refused by the foreign key. The seed command accepts only a development or test database (`apps/api/src/config/db-guard.ts`), so the way the base lists (this one, like `gender`) reach staging and production is part of the release procedure T3.0 writes here. The migration rewrites the table `beneficiaries` once (a stored generated column). Its rollback is described beside the table in `docs/database/DATABASE_SCHEMA.md`: run `down.sql` in one transaction, and read its WARNING, which counts the rows it kept and that stay frozen.

Deploy note, the name keys (D-174): migration `20261114120000_beneficiary_name_keys` adds the key columns empty (no rewrite) but builds three indexes on `beneficiaries` (the two of the pair queries and the one of the missing or older keys) and two on `beneficiary_family_members` with a plain `CREATE INDEX`, as every migration of this repository does: Prisma runs a migration in one transaction, where `CREATE INDEX CONCURRENTLY` is not allowed, and no migration here builds one concurrently. A plain build blocks every write to the table it indexes until it ends, so on a database whose `beneficiaries` holds many rows (2,000,000 in the measurement data set) this migration holds the beneficiary writes (submissions, contact edits, merges) for as long as the builds take and runs outside working hours. Reads go on during the build. After `pnpm db:migrate` (whose `jobs:install` step creates the `name-keys` queue with its policy `stately`: one run waiting and one running at most), the worker's start finds the profiles without keys and queues the key job, which fills them in batches of 2,000 rows; the starting spelling variants come from the base seed (see the note above on how base data reaches staging and production).

Deploy note, the times helped (D-172, BR-307): migration `20261115120000_beneficiary_help_counters` adds `beneficiaries.help_count` and `max_helps_in_year` with a constant default (no table rewrite), counts every profile from what is on file in one UPDATE, and builds two plain indexes. On the measurement data set (2,000,000 beneficiaries, 500,000 applications, 187,500 people helped; docs/testing/PERFORMANCE.md) the whole migration took about 61 seconds, the UPDATE alone 57.6 (the count itself 1.2 s; the rest is writing the rows and their many indexes), the two indexes 2.2 and 0.5 s. Every write to `beneficiaries` waits while the migration runs (Prisma runs it in one transaction, and the indexes are built with a plain `CREATE INDEX`, not `CONCURRENTLY`): about a minute on two million profiles, next to nothing on today's production, which holds no beneficiary yet. Run it in a quiet window all the same. `pnpm db:migrate` (`jobs:install`) creates the `help-counters` queue; the worker schedules the nightly recount at 03:00 Dhaka time. Its `down.sql` drops the two columns, their CHECK and indexes and gives the table the update-stamp trigger of the name keys again.

Deploy note, the list of whose name stands beside a person (D-174): migration `20261114180000_beneficiary_guardian_relation` adds `beneficiaries.guardian_relation_code`, whose codes (`father`, `husband`) come from the reference list `guardian_relation` of the base seed and not from the migration, as for the list of whose number a mobile is above: until the base seed has run, every code is refused by the foreign key and a form's question for the column has no options. The migration rewrites the table `beneficiaries` once (a stored generated column) and builds one plain index, so on a large table it holds the beneficiary writes while it runs. Its `down.sql` drops the column with its values.

Deploy note, the levels of the suggested pairs (D-174): migration `20261114220000_beneficiary_pair_levels` adds `beneficiary_merge_candidates.level` as NOT NULL with a CHECK that ties it to the rules. The API of the release before it does not write that column, so every refresh of a person's pairs it makes (a submission, a contact edit, a correction, a merge) fails on the NOT NULL, and with it the write that called it. The migration and the API of this release therefore go out together, in this order: stop the API and the worker, run `pnpm db:migrate`, then start the API and the worker of this release. Never run this migration under the old API. Its `down.sql` drops the level and the new rule again, so a rollback runs it after the new API is stopped and before the old one starts.

Deploy note, the project series (D-176): migration `20261116120000_project_series` creates `project_series`, makes every existing project the one session of its own series, and sets `projects.series_id`, `period_from` and `period_to` NOT NULL. The API of the release before it writes none of the three, so every project it creates fails on the NOT NULL. The migration and the API of this release therefore go out together, in this order: stop the API and the worker, run `pnpm db:migrate`, then start the API and the worker of this release. The migration reads and writes `projects` only (one row per project), so it takes no measurable time; it leaves each project's update stamp as it was. Its `down.sql` runs after the new API is stopped: it restores the unique project code and drops the series, the periods and the program descriptions, and it stops before changing anything while two sessions carry one code (see `docs/database/DATABASE_SCHEMA.md`, "projects").

Deploy note, the year of a cancelled session (D-177): migration `20261116130000_cancelled_session_year` replaces the two unique indexes of a session's year (`projects_series_id_year_key`, `projects_code_year_key`) by partial ones that leave cancelled sessions out, and adds the plain index (series_id, year). It rewrites no row and rebuilds three small indexes of `projects`, so it takes no measurable time and needs no order with the API: the API of the release before it keeps working, it only still refuses a year a cancelled session holds. Its `down.sql` restores the full uniques and stops before changing anything while a cancelled session shares its year with another session of its series (`cancelled_session_year_in_use`, with the code and the year): which of the two keeps the year is the owner's decision, no row is removed to make room.

Deploy note, the cover photos (D-176): migration `20261116140000_cover_photos` replaces two CHECK constraints (`files_kind_check`, `file_links_entity_type_check`) by wider ones. Each is validated against its table under a short exclusive lock, one read of `files` and one of `file_links`; on the present sizes that is well under a second, and on a much larger `files` table it should run while no upload is being finalized. It needs no order with the API: the API of the release before it never writes the new kind. The covers are stored in the `photos` bucket under `covers/`, with every other photo, so the backup and the copy between storage drivers already include them. Its `down.sql` runs after the new API is stopped: it removes the cover links and keeps the photos as files.

Release note, a repeat in the same project (D-172, BR-306): a project whose application form component carries no `repeat_person` or `repeat_family` setting reads both as `hold`, the decided defaults. From this release that also covers a probable same-person pair (two live profiles whose name, father's or husband's name and village give the same keys in one union) and a person listed in another applicant's family in the same project. Behaviour change for existing projects: approvals of a repeated person or family member in the same project now ask a reason unless the PM switches the project to tell. Tell the Program Managers before the release, so a project that wants the earlier, quieter review switches its two settings to "only tell" in the project setup.

Deploy note, the beneficiary statistics (D-179): migration `20261117200000_beneficiary_statistics_indexes` builds two indexes with a plain `CREATE INDEX`, as every migration of this repository does (Prisma runs a migration in one transaction, where `CONCURRENTLY` cannot run): `beneficiaries_live_block_gender_idx` on the live profiles and `applications_project_help_idx` on the applications. Each build holds the writes of its table while it runs; on the measurement data set (2,000,000 beneficiaries, 500,000 applications) they took about 3 and 1 seconds, so the migration runs in a quiet moment, as the earlier index migrations do. Migration `20261117180000_upload_finalize_lease` adds a nullable column and replaces a trigger and a function; it rewrites no row.

Deploy note, the shipped reference data (D-179): the roles and permissions, the workflow templates and the base reference lists used to come only from the development seed, which refuses every database but development, test and the measurement one. From this release `pnpm db:migrate` ends with `reference:sync` (`apps/api/scripts/reference-sync.ts`), which inserts what a database is missing and changes no stored row: an entry an administrator renamed or switched off stays as it is, and a role or permission no longer in the file stays (as the seed reports it). A stored workflow template whose content differs from the shipped template of the same version is left as it is and printed as a WARNING: a changed template reaches production only as a new version, since a project keeps the snapshot of the version it was activated with. The script reads `docs/security/permissions.yaml` and `docs/architecture/workflow-templates/` from the build, so the T3.0 images carry both. The two notes above that ask for the base seed after `pnpm db:migrate` (the lists `mobile_owner` and `guardian_relation`) are met by the sync. Its rows carry the same ids as the seed's, so the development seed run after it updates them in place.
