# ROLE-BASED ACCESS CONTROL AND DATA SCOPES

Status: complete, task T0.10 (2026-10-10). Design only; no code. Companion file: `docs/security/permissions.yaml`, the machine-readable single source of truth. Every permission name in this document exists in the YAML and every YAML permission is described here (verified by the T0.10 name check; regenerated by the implementation's matrix test from T1.8). Sources: blueprint A4 (both matrices, permission panel), A5 (permission sets), B4 (scopes and implementation rules), B8 (field-level protection); constitution §5, §13; rules BR-180…193; decisions Q-36, Q-45, Q-46, O-05, O-24, O-25; `docs/architecture/AUTH.md`; `docs/architecture/SYSTEM_ARCHITECTURE.md` §6.

## 1. Model

- **Permission = role × data scope.** A grant is a triple (permission name, scope, optional condition). Holding `application.approve` at REGION means: approve applications of projects where the user is RPM, inside the user's region.
- **Default deny.** An action is allowed only if a grant exists for the user from one of four sources, in this order of evaluation: (1) `global_scope: true` on the role (Department Head, Monitoring Team: every permission at GLOBAL, minus `global_roles_excluded`), (2) the role's default grants in the YAML, (3) the project-level permission set or project grant (`project_volunteers.permission_set`, `project_volunteers.extra_permissions`, `project_staff`), (4) a permission-panel override (`user_permissions`: grant or revoke, with scope). A revoke override wins over any grant.
- **Project-level.** Volunteers get permissions only through the permission set assigned on each project (A5); the same person holds different sets on different projects (Q-16). Officials get REGION/PROGRAM defaults from their role, narrowed to the projects and areas they are assigned to.
- **No hard-coded permission.** The API never tests a role name to allow an action; it tests a permission name (BR-193). Role names appear only in the YAML defaults and in the permission panel UI.

## 2. permissions.yaml schema and loading

```
version, scopes[], conditions{}, roles{}, permission_sets{}, sensitive_fields[], permissions[]
permission: { name, description, module, sensitive, default: [ { role, scope, condition? } ], global_roles_excluded? }
```

- Names are `resource.action[.qualifier]`, lower-case, dotted, unique.
- `module` is the MODULE_CATALOG id (M01…M22).
- `sensitive: true` marks permissions that expose a protected field class or export it; such actions are always audited (BR-179, BR-224).
- `conditions` are named checks implemented once in the `access` module (for example `house_construction_only` reads the project's workflow template; `if_rpm_grants` means the default is absent and the grant must come from `project.volunteer_grant.manage`).
- Loading (T1.8, built): `apps/api/src/access/registry.ts` validates the file with a zod schema and cross-checks it (roles, sets, conditions, `extends` cycles) when the container starts, and the API and the worker refuse to start on any problem; `PERMISSIONS_FILE` may point elsewhere (DEPLOYMENT). `createContainer` also refuses a YAML condition without a check in `access/conditions.ts`. `defineRoute` refuses a route whose permission is not in the file, whose scope entity is unknown, or whose permission is held below GLOBAL while the route declares the entity `none`. A YAML permission that no endpoint uses yet is listed in the matrix report instead of stopping the start (D-077).
- The authorization-matrix test (`apps/api/test/integration/authorization-matrix.test.ts`) calls every registered endpoint as every role and as an anonymous caller and compares each decision with the role's default grants; its report is `docs/security/AUTHORIZATION_MATRIX.md` (regenerate with `pnpm --filter @css/api authz:matrix`). The scope dimension (which records) is tested by the scope and IDOR tests (section 10).
- The matrix tables in section 5 are a human view of the same data. When the two disagree, the YAML wins and this document is corrected.

## 4. Data scopes and their resolution

| Scope | Meaning | Resolved from |
|---|---|---|
| GLOBAL | Whole country, all programs | `roles.global_scope` or an explicit GLOBAL grant (volunteer and beneficiary tabs for officials, BR-185) |
| PROGRAM | All projects of the programs the user manages | `programs.pm_user_id` (and panel grants naming a program) |
| PROJECT | A specific project | `project_volunteers` rows, `project_staff` rows, Procurement attachment to house-construction projects |
| REGION | Own region (division) inside assigned projects | `project_areas` rows where the user is RPM; staff under an RPM inherit the RPM's region through `project_staff`; Official দায়ী and Implementer through their project assignment |
| DISTRICT / UPAZILA / UNION | When the PM split districts among RPMs, or by assignment | `project_areas.location_id` (district rows when the PM split districts) for the RPM; Local দায়ী and Paid Volunteer assignments carry location ids |
| ASSIGNED | Only own assigned beneficiaries or applications | `work_assignments` (Local দায়ী), paid-volunteer assignments, site-verification assignments, Official দায়ী's area |
| SELF | Own created applications, own profile, own sessions | `applications.owner_volunteer_id`, `applications.created_by_user_id` (team members, `own_created`), `users.id` |

Resolution rules:

- Volunteers outside any project (D-084): a pending or unassigned volunteer is reached through the address. REGION and the area scopes reach volunteers whose division, district, upazila or union is one of the caller's area locations; PROGRAM reaches those in the area locations of the program's projects; GLOBAL reaches all. This is how the approvers of Q-19 see the registrations of their region.

- The resolver computes, per request, the set of scope instances the user holds for the target entity type (for example `{REGION: [projectA/divisionX], PROJECT: [projectB]}`) and the repository turns it into a mandatory `WHERE` clause (SYSTEM_ARCHITECTURE §6 step 7). A user with no instance for the entity type gets an empty result, never an error that reveals existence.
- Several scopes add up: an RPM who is also assigned as Official দায়ী on another project holds REGION for the first and the Official দায়ী grants for the second.
- GLOBAL read of the volunteer and beneficiary tabs does not imply write: writing still needs the specific permission at its scope (BR-185).
- District split (Q-08, O-09): when `project_areas` names districts for an RPM, REGION for that RPM means those districts only; until then every RPM of the division sees the whole division.
- Scope instances are cached per request only; permission changes bump `permission_version` and force a token refresh (AUTH.md §9).

## 7. Permission panel

- Available only to the Department Head and the Monitoring Team (`permission.panel.manage`, implied by `global_scope`). PMs and RPMs may view effective permissions (`permission.view`) but change them only through the project-level grants of section 6.
- The panel grants or revokes any permission for any user at a chosen scope instance (GLOBAL, a program, a project, a region/district, ASSIGNED, SELF). A revoke override beats every grant source. Overrides live in `user_permissions` with granted_by, reason, time, optional expiry.
- Every change writes an audit entry (`permission_change`) with old and new effective grants (BR-180) and bumps `permission_version` so active sessions refresh immediately (AUTH.md §9).
- The panel cannot: give `system.owner.transfer` to anyone but the Department Head; remove the Department Head's or Monitoring Team's global scope; grant a sensitive permission to a volunteer role (hard rule: volunteers never see ratings, categories, NID, bank, donor data, official sections, BR-046, BR-183). Attempts are refused and audited.
- Built in T1.8 (`apps/api/src/services/access.ts`, screen SCR-062 at `/admin/permissions`): the refusals answer 403 `permission.grant_refused` with `params.rule` (D-078) and are audited as `permission_change_refused` in a transaction of their own; any change that targets the Main Admin answers 409 `user.system_owner_protected` before every other rule and is audited the same way. The checks run inside the change's transaction with the target's user row locked. An override names a scope reference that must exist and fit the scope type (a program, a project, or a location of the level REGION = division, DISTRICT, UPAZILA, UNION; none for GLOBAL, SELF, ASSIGNED). An override ends with `POST /permission-grants/{id}/revoke`; effective-permission rows of source `panel_grant` carry that `grantId` (D-079, proposed). Project grants (`POST /projects/{id}/grants`) replace the target's extras on that project; each newly added permission must carry an `if_rpm_grants` default and be held by the granter on that project, extras already there may stay or go. Roles stay read-only on the panel (O-61). Blocking an account (state `blocked`) and lifting a block are for the Department Head alone, even with a panel-granted `user.state.change` (D-080).
- The same person may hold different sets on different projects: the panel and the project grants both key on (user, project) where the scope is PROJECT or narrower.

## 8. Server-side enforcement

As built in T1.8 (Express, ADR-014; the decorator names below are the design's, the code declares the same on `defineRoute`):

- `requireAccess` (`apps/api/src/auth/require-access.ts`) runs token → session → permission version → account state → permission → scope. The permission check asks whether any effective grant names the route's permission (`access/effective.ts`: GLOBAL roles, role defaults, project permission sets and extras, panel overrides; a revoke wins, an expired override counts as absent). A refusal answers 403 `permission.denied` and logs a `permission_denied` event with user, permission, entity and request id only (NE-LOG-03).
- The scope handle (`access/scope.ts`, made only by `AccessService.scopeFor`) holds the instances for the route's permission and entity: GLOBAL, SELF, programs, projects, areas and, for the user entity under `own_region`, volunteer-only areas; panel revokes of an instance (a program also removes its projects) are subtracted. Conditions narrow a grant for the entity or drop it; a condition the entity has no rule for denies. Routes of the entities `none`, `global` and `system` filter no data and therefore need an unconditioned GLOBAL grant.
- Services receive the handle (`scopeOf(req)`) and filter with `userWhere` / `projectWhere`; single records are loaded with `AccessService.findUser` / `findProject`, which answer 404 `permission.not_found` outside the scope (logged as a denial) before any write. Filters for applications, beneficiaries and volunteers come with their endpoints (T2.x).
- The field mask (`access/field-mask.ts`) runs in `defineRoute` on every success response: the route's response schema marks protected fields with `sensitive(schema, class)` (and form-answer arrays with `officialRows`), the data is parsed through the schema (undeclared keys never leave) and the classes the caller's roles may not see are removed. A route of the entities volunteer, beneficiary, application, project, program or file, or with `sensitiveFields`, must declare a response schema; a schema may mark only the classes the route declares.


1. **Guard declaration per endpoint.** Every handler declares `@Permission('<name>')` and `@ScopeOf('<entity>')`; a handler without them cannot be registered (boot-time check). Anonymous endpoints (public form, login, OTP) declare `@Public()` explicitly and are listed in SECURITY_POLICY.
2. **Check order.** Rate limit → authentication → role resolution → permission → scope resolution → object-level → validation → service (SYSTEM_ARCHITECTURE §6).
3. **Scope resolution per role** (section 4) produces query filters; repositories accept a scope object and never a raw user id.
4. **Object-level checks for ASSIGNED and SELF.** Single-record routes load the record through the scoped repository; a record outside the scope is "not found" (404), never 403, so existence is not leaked. SELF compares `submitted_by`/owner to the user; ASSIGNED requires an assignment row. Team members additionally require `created_by = user` (`own_created`).
5. **IDOR prevention.** All ids are UUIDs (O-03), never sequential; list endpoints always filter by scope; batch endpoints (sync, bulk update) check each record's scope individually and report per-record results; file downloads go through the permission check before a signed URL is issued (BR-204).
6. **Field-level protection.** The `sensitive_fields` catalogue of the YAML drives one serializer mask used for JSON responses, exports (CSV/XLSX/PDF) and PDF reports alike (BR-183). Protected classes: beneficiary NID/birth number and NID photo; volunteer NID and NID photo; volunteer bank details; ratings, categories and their comments; donor data; official form sections and scores; blocklist reasons; audit detail. Masking is by removal, not by blanking, so a volunteer client never learns the field exists. The one exception is the own record (D-081): `GET /volunteers/me` returns the volunteer's own NID, NID photo id and bank details in full.
6a. **Per record in nationwide lists (O-67, D-094).** The volunteer and beneficiary tabs are GLOBAL through `volunteer.view_all` / `beneficiary.view_all`, while the protected permissions are scoped. So a protected field leaves only when its class is visible to the caller **and** the record lies inside the caller's scope for `volunteer.view_sensitive` (identity and bank) or `beneficiary.view_nid` (NID, birth registration); the file route decides NID photos the same way. A filter or a search on a field outside the caller's classes answers 403, so it cannot reveal what the answer hides. A PROJECT-scoped caller (the Procurement Team) sees only the rows of its own projects inside a beneficiary profile. Classes added for the tabs: `beneficiary.contact`, `beneficiary.address_detail`, `beneficiary.care`, `beneficiary.profile_detail`, `beneficiary.application_history`; together they leave the Media and Procurement Teams exactly the allow-list of O-67.
7. **Sensitive exports** (`sensitive: true` permissions, `export.*` of identity fields) write an audit entry with the filter used and the row count (BR-224, BR-179).
8. **Default deny** at every layer: a missing grant, an unknown permission name, an unresolved scope or a failed condition all deny.

## 9. Special cases

- **Main Admin:** `system.owner.transfer` is the only permission the Monitoring Team lacks; the Department Head account cannot be deactivated, blocked or stripped by anyone (AUTH.md §11, BR-035).
- **Blocked users:** authentication succeeds but every permission check fails with `account_blocked`; the block message endpoint is `@Public`-like for authenticated blocked users only (BR-047).
- **Pending users:** only `edit_request.submit`-class self endpoints and own profile read.
- **Handover:** `user.handover` reassigns ownership rows; permissions of the leaving official are revoked at deactivation (AUTH.md §10).
- **Needs-verification records:** visible to RPM and Executive of the region (`application.verify_needs_verification`); the volunteer sees the record's status only.
- **Public form:** anonymous `@Public` endpoint creating a needs-verification application; rate-limited (O-08); no read-back of other records.
- **Jobs and sync processing:** run application services with a system actor plus the originating user's id; the service re-checks the originating user's permission and scope as if the request were online.
- **Procurement `issue.resolve`:** condition `own_or_paid_volunteer_issues` evaluated against `issues.raised_by` role (Q-46).
