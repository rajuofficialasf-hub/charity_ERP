# INTERNATIONALIZATION

Status: complete for Phase 0, written in task T0.20 (2026-10-10); implemented in task T1.5 (2026-10-11; D-067, O-56; §13). This document is binding for every package that shows, stores, sends or exports text.

Sources and precedence: constitution §11; BUSINESS_RULES BR-218 to BR-220, BR-243 to BR-245 (BR-221 retired); owner decisions UX-05 (English digits), O-42 (Taka display), O-43 (bilingual configuration, no Hijri, no runtime overrides, 12-hour time) and the technical choices O-44 in `docs/DECISION_LOG.md`; API_STANDARDS §7 and §8; NOTIFICATIONS §6; DATABASE_SCHEMA §2 (bilingual columns); DESIGN_SYSTEM §2.5 and §3. Where this document and an older one differ, the decision log wins and the older document is corrected.

## 1. Principles

1. **Two first-class languages.** Bangla (`bn`) and English (`en`) are complete in every screen, message, template and export. Bangla is the default for everyone and the source language of the catalogue (BR-218).
2. **Per-user choice.** Each user picks a language; the choice follows them on every device.
3. **No hard-coded user-facing text.** Every label, button, menu, status, validation message, error, notification, email, SMS, report heading and export header comes from the catalogue or from bilingual data (§3, §7).
4. **English digits everywhere.** All numbers (amounts, dates, times, counts, ids, phone numbers) use 0-9 in both languages (UX-05, BR-219), produced only by the central formatter (§6).
5. **Data is not translated.** Names, addresses, comments and stories typed by people are stored and shown exactly as typed. Only configuration text (form labels, option lists, status names, document names and similar) is bilingual data.
6. **A third language is configuration, not a rewrite** (§11).

## 2. Languages and locale resolution

| Item | Rule |
|---|---|
| Supported locales | `bn`, `en` (list `L-locale`, DATABASE_SCHEMA §5.1), mirrored by the constant `SUPPORTED_LOCALES` in `packages/shared/i18n` |

| Before login | The language switch writes the cookie `css_locale` and a copy in local storage (both read by the browser at start-up, D-067 as amended by D-073); after login the stored `users.language` wins and is written to the same stores (T1.7, O-56) |

| API requests | The PWA sends `Accept-Language: bn` or `en` on every request. The API resolves the language as: `Accept-Language` if it is a supported locale, else the authenticated user's `users.language`, else `bn` (API_STANDARDS §7) |
| Messages sent later | Rendered in the recipient's language, not the actor's (§5) |
| Offline | The catalogue of the current language is part of the precached app shell (OFFLINE_SYNC.md); the other language is fetched on switch and then cached. Switching language never loses offline drafts |

## 3. Message catalogue

### 3.1 Layout

```
packages/shared/src/i18n/            (entry @css/shared/i18n; D-067)
  messages/
    bn/  common.json  nav.json  ui.json  home.json  errors.json  codes.json  gallery.json  ...
    en/  (the same files)
  catalogue.ts            NAMESPACES, START_NAMESPACES and both whole catalogues; MessageKey type inferred from the bn JSON
  bn-start.ts  bn-rest.ts the Bengali start and rest parts (entries @css/shared/i18n/bn-start, bn-rest; §3.4)
  en-start.ts  en-rest.ts the English start and rest parts (entries @css/shared/i18n/en-start, en-rest)
  catalogue-bn.ts  catalogue-en.ts   a language's whole catalogue, its two parts together
  bilingual-columns.ts    registry of bilingual data fields (§7.1, §11)
  index.ts                SUPPORTED_LOCALES, DEFAULT_LOCALE, resolveLocale, translate (server t())
packages/shared/src/format/          (entry @css/shared/format; §6)
```

Module namespaces (auth, registration, volunteer, beneficiary, project, form, application, activity, distribution, dawah, notification, sync, file, export, admin) are added by the tasks that build those screens. `ui` holds the design system's own texts: since D-150 the `asf` group, the words of the asf pieces (`UiLabels` of `apps/web/src/ui/contract.ts`: "required", "close", pager words), passed to the asf `UiProvider` (the earlier groups of `UiMessages` left with `packages/ui`); `gallery` holds the texts of the dev-only asf gallery (`/dev/asf`) and is used only by that route (it sits in the rest part, §3.4).

The same JSON files serve the web app (use-intl, D-073), the API (server-side `t()`), the worker (notification and export rendering) and the tests. There is one catalogue, not one per app (constitution §13, no duplicated logic).

### 3.2 Namespaces and keys

| Namespace | Holds | Example key |
|---|---|---|
| `common` | Shared words, actions, states (save, cancel, retry, empty, loading) | `common.action.save` |
| `nav` | Menus, tab bar, breadcrumbs | `nav.review` |
| `auth`, `registration` | Login, OTP, registration, sessions | `auth.login.submit` |
| `volunteer`, `beneficiary`, `project`, `form`, `application`, `activity`, `distribution`, `dawah`, `admin` | Screen texts per module | `application.review.approve` |
| `notification`, `sync`, `file`, `export` | Inbox texts, offline and sync texts, upload states, export dialogs | `sync.banner.offline` |
| `codes` | Labels of fixed system code lists (DATABASE_SCHEMA §5.1), one key per code | `codes.job_status.queued` |
| `errors` | One message per API error code (API_STANDARDS §8) | `errors.validation.nid_format` |

Rules:
- Keys are dotted, lower-case snake segments: `namespace.area.element` (`application.review.reason_required`). A key names its purpose, never its text.
- Keys are stable. Renaming a key is a refactor done in one commit across code and both catalogues.
- Workflow state and stage names, reference-list labels, role and permission names, and form texts are **bilingual data**, not catalogue keys (§7). The catalogue holds only text that ships with the code.
- Notification templates are seeded from `packages/shared/notifications/templates` with their own keys and versions (NOTIFICATIONS §6); they follow the same language rules but live in that folder, not in `messages/`.

### 3.3 Message syntax (ICU MessageFormat)

| Need | bn | en |
|---|---|---|
| Parameter | `"{name}-এর আবেদন অনুমোদিত হয়েছে"` | `"{name}'s application was approved"` |
| Plural (counts are formatted by the formatter) | `"{count}টি আবেদন"` | `"{n, plural, one {{count} application} other {{count} applications}}"` (`n` the number, `count` the formatted text) |
| Select | `"{gender, select, female {তিনি} male {তিনি} other {তিনি}}"` | `"{gender, select, female {she} male {he} other {they}}"` |
| Number and date parameters | Passed already formatted by `packages/shared/format` (§6) as strings, never with ICU `number`/`date` skeletons and never as `#`, so digits and grouping stay identical everywhere: ICU would format numbers with the `bn` locale in Bengali digits (D-067). A plural selector argument is not displayed | same |
| Rich text | `"<link>সংশোধনের অনুরোধ</link> পাঠান"` with a tag mapped to a component | `"Send a <link>correction request</link>"` |

- Sentences are never built by concatenating fragments; word order differs between the languages.
- Bangla has no grammatical plural for counted nouns ("3টি আবেদন"), so bn usually needs only `other`; en needs `one` and `other`. The catalogue check (§4) verifies that both messages declare the same parameters.
- Messages contain no digits written into the text (UX-05 check) and no HTML except mapped rich-text tags.

### 3.4 Typed keys and loading

- Keys are typed by inference from the bn JSON (use-intl `AppConfig` on the web, the `MessageKey` path type on the server; D-067); `t()` accepts only known keys, so a typo fails the typecheck.
- The web app loads one language at a time (D-104), each in two parts (D-173), one chunk each: the start part (`@css/shared/i18n/bn-start`, `en-start`) and the rest (`@css/shared/i18n/bn-rest`, `en-rest`). The server and the tests use the whole catalogue of both languages through `@css/shared/i18n` (`@css/shared/i18n/bn` and `en` stay as whole-catalogue entries), and the typed keys are the whole catalogue's. Both languages of a namespace have the same keys, so switching language swaps files without code changes.
  - The start part holds the namespaces the sign-in page and the frame around every page render, named in `START_NAMESPACES` in `packages/shared/src/i18n/catalogue.ts`: `auth` (the sign-in page and its form), `common` (the system name of the sign-in frame, the language switch, the route error, the session provider's loading state), `errors` (the sign-in form's validation through `useSchemaResolver`), `notifications` (the notification bell of the top bar asks for its namespace on every page), `registration` (the link to the volunteer registration under the sign-in form) and `ui` (the asf UI system's words, handed to its provider around every page). Every other namespace is in the rest.
  - The device language's start part is loaded before the first render (`loadMessages` in `apps/web/src/i18n/locale.ts`, awaited by `main.tsx`). Every lazy route of `apps/web/src/routes/index.tsx` loads through `withRest`, which awaits the page's module and the rest of the shown language together, so a page renders only with every text; the eager sign-in route does not wait. The locale provider re-renders when a part arrives and hands use-intl the merge of the loaded parts.
  - A switch loads the new language's start part, and its rest too once a page has asked for the rest, and takes effect when they have arrived; the form builder's preview loads both parts of the other language (`loadCatalogue`). A failed load is tried again. The service worker precaches every chunk, so both parts of both languages open offline in an installed app.
  - Adding a namespace: add its JSON file in both languages, import it in `bn-start.ts` and `en-start.ts` and name it in `START_NAMESPACES` only if the sign-in page or the always-mounted frame renders one of its texts, otherwise import it in `bn-rest.ts` and `en-rest.ts`; add it to `NAMESPACES`. The type of each part and a test of `packages/shared/test/i18n.test.ts` fail when a namespace is in neither part or in both.

## 4. No hard-coded strings: rule and enforcement

Rule (BR-218): no user-facing text appears as a literal in source code. Allowed exceptions: log messages and developer-only error text, identifiers and codes, CSS class names, test fixtures, seed data files and the catalogue itself.

Enforcement (O-44 item 2), all running in CI from T1.5 and failing the build:

| Layer | What it catches |
|---|---|
| ESLint rule `css/no-literal-ui-text` (local rule in `packages/config`, D-067) in `apps/web/src`, the asf template included | JSX text and the attributes `placeholder`, `title`, `aria-label`, `alt`, `label` given as string literals instead of `t()` |
| No-Bengali-script check | Any character of the Bengali block (U+0980 to U+09FF) in `.ts`/`.tsx` files outside `packages/shared/i18n/messages`, notification templates, seed data and test fixtures: hard-coded Bangla in the API or the web app |
| Catalogue check script | bn and en have the same keys; both messages of a key declare the same ICU parameters; every message parses; no value contains Bengali digits (U+09E6 to U+09EF) (UX-05); every key used statically in code exists; unused keys are reported as warnings; every error code in API_STANDARDS §8 has `errors.<code>` in both languages; every notification template key exists in bn and en for each channel (NOTIFICATIONS §6) |
| Typed keys | Unknown keys fail `pnpm typecheck` |
| Pseudo-locale (development only) | A generated `qps` locale wraps every catalogue string in markers; any unmarked text on screen is hard-coded. It is never offered to users or shipped to production (set the cookie `css_locale=qps` in `vite dev`) |

Implementation (T1.5): the lint rule is `packages/config/eslint-rules/no-literal-ui-text.mjs`; the catalogue check and the no-Bengali-script check run in `scripts/check-i18n.mjs` (`pnpm i18n:check`, part of `pnpm lint`). The script reads `checkCatalogue()` from `@css/shared/i18n`, collects the error codes from API_STANDARDS §8 and the guards of WORKFLOW_ENGINE §6, skips comments (documentation is not user-facing), allows the taka sign ৳ in code, and accepts a data-matching pattern only on a line marked `i18n-allow-bengali` with a reason (used for place-type words in the locations converter).

## 5. Server-side localization

| Output | Language | Rule |
|---|---|---|
| API error and validation messages | Request language (§2) | The response carries `code`, `messageKey` and the rendered `message` (API_STANDARDS §3, §7); clients may re-render from `messageKey` |
| In-app notifications | The reader's current language at read time | The `notifications` row stores the template key and parameters, not rendered text (NOTIFICATIONS §7), so a user who switches language sees the inbox in the new language |
| Email, SMS, push | The recipient's `users.language` when the message is queued | People without an account (Qurbani donors, BD-32 to BD-34) receive `bn`; no language field is kept for them |
| Exports (CSV, XLSX, PDF) | The requester's language at request time | Stored in `export_jobs.locale` (DATABASE_SCHEMA) so a retried job renders the same language |
| Background jobs (deadline warnings, alerts) | Per recipient as above | Jobs never format text in the server's own locale |
| Audit log | Language-neutral | Entries store action codes, field keys and raw values; the audit viewer renders labels in the viewer's language |
| Dates and numbers in any server output | English digits | Always through `packages/shared/format` (§6) |

## 6. Number, date and time formatting

### 6.1 One formatter

All formatting goes through `packages/shared/format`, used by the web app, the API, the worker and the export service. No component, query or template formats a number or date by itself (BR-219).

- Locale tags: `bn-BD-u-nu-latn` and `en-IN-u-nu-latn`. The `-u-nu-latn` extension forces Latin digits; without it the `bn` locale returns Bengali digits (Intl test, 2026-10-10).
- The digit system is one constant (`DIGITS = 'latn'`). Showing Bengali digits later needs a new owner decision and a change of that constant only (constitution §11).
- Raw Intl output is not used directly where it differs from the agreed format: Intl writes "10/10/2026" and "4:40 pm", so the formatter assembles dates and times from `formatToParts` and its own day-period table (§6.3).
- Time zone for display: `Asia/Dhaka` always; timestamps are stored in UTC and business dates as plain dates (DATABASE_SCHEMA §2).

### 6.2 Formats

Examples use 10 October 2026, 16:40 Dhaka time.

| Function | Use | bn | en |
|---|---|---|---|

| `formatDecimal(n, max=2)` | Averages, quantities | 28.8 | 28.8 |
| `formatPercent(r)` | Shares, progress | 62% | 62% |
| `formatTaka(n)` exact | Entry fields, payment and ledger rows, vouchers, exports, PDF reports (O-42) | ৳ 12,60,000 | ৳ 12,60,000 |
| `formatTaka(n, {summary: true})` | Dashboards and summaries; below 10 lakh lakh grouping, from 10 lakh in millions with at most 2 decimals, trailing zeros dropped; the exact amount is available on focus or in the detail (O-42) | ৳ 3,00,000 · ৳ 1 মিলিয়ন · ৳ 1.26 মিলিয়ন | ৳ 3,00,000 · ৳ 1 million · ৳ 1.26 million |

| `formatDateLong(d)` | Headings of letters and PDF reports | 10 অক্টোবর 2026 | 10 October 2026 |

### 6.3 Day periods for 12-hour time (O-43)

| Time | bn period | en |
|---|---|---|
| 0:00 to 3:59 | রাত | AM |
| 4:00 to 5:59 | ভোর | AM |
| 6:00 to 11:59 | সকাল | AM |
| 12:00 to 15:59 | দুপুর | PM |
| 16:00 to 17:59 | বিকাল | PM |
| 18:00 to 19:59 | সন্ধ্যা | PM |
| 20:00 to 23:59 | রাত | PM |

bn writes the period first ("সকাল 9:05", "রাত 12:40"); en writes it after in capitals ("9:05 AM", "12:40 AM"). The boundaries follow the CLDR Bengali day periods, with "রাত" instead of CLDR's "রাত্রি".

### 6.4 Input parsing and normalization (O-44 item 4)

- Every user-entered text is normalized to Unicode NFC at the API boundary (a zod transform in the shared schemas) before validation, storage and comparison. Bengali letters such as য় and ড় have more than one encoding; without NFC, search, `pg_trgm` duplicate candidates (O-39) and unique checks would treat equal names as different.
- Number, money, NID, birth-registration and phone inputs accept Bengali digits and convert them to 0-9 as the user types (DESIGN_SYSTEM §5.4); thousands separators and spaces are stripped before validation.
- Dates are entered with the date picker of the design system at every size (O-55): segments in dd-mm-yyyy order with English digits, calendar as a popover on desktop and a bottom sheet on phones.
- No Hijri date is shown or accepted anywhere (O-43); BR-221 is retired.

## 7. Bilingual data

### 7.1 Where it lives

| Source | Bilingual fields |
|---|---|
| Database tables with `*_bn`/`*_en` columns (DATABASE_SCHEMA) | roles (name), locations (name), reference_lists (label), holiday_calendar (name), programs (name, description), project_series (name, description), projects (name), project_templates (name), forms (title), form_sections (title), form_fields (label), field_options (label), form_library_sections (title), form_library_fields (label), workflow_definitions (title), dawah_syllabus_topics (title), documents (name) |
| JSONB | `projects.rules` (four bilingual texts, `ProjectRules`), `document_templates.rows` (name_bn, name_en), the workflow snapshot (state and stage labels) |
| Workflow templates (`docs/architecture/workflow-templates/*.yaml`) | `title_bn`/`title_en`, state and stage `label_bn`/`label_en` (schema.json requires both) |
| `docs/security/permissions.yaml` | role `name_bn`/`name_en`; permission names shown in the permission panel come from the catalogue `admin.permission.<name>` |
| Notification templates | One row per key, channel and locale (NOTIFICATIONS §6) |
| Fixed system code lists (DATABASE_SCHEMA §5.1) | Not stored as data: labels come from the catalogue `codes.<list>.<code>` |

`packages/shared/i18n/bilingual-columns.ts` lists every bilingual table and field above. The rendering helper, the translation screen (`i18n.manage`), the third-language migration (§11) and a schema test (every listed column exists in both languages) all read this registry.

### 7.2 Storage and validation

- Both languages are `not null` for every configuration text (DATABASE_SCHEMA §2), and both must be filled (O-43, BR-245): the form builder refuses to publish a version, and project setup refuses to activate a project, while any English or Bangla text is missing; the error lists each missing field.
- The shared zod type `bilingualText` (`{ bn: string, en: string }`, both trimmed, NFC-normalized and non-empty) is used by every API that writes bilingual data; the service maps it to the column pair.
- Drafts (form drafts, project drafts, templates) may be saved with missing English text; the editors show a "translation missing" marker per field and a count in the header.
- A form draft may wait for any of its texts in either language, or in both (D-171): a part's title, a question's label, help text and placeholder, an option, a number table's row and column, a calculation's text result. The form engine (`packages/shared/src/forms/definition.ts`) accepts the empty string in a draft and stores it trimmed, so a text of only spaces is missing; at publish `checkDefinition` reports `form.label_language` once per text and language, and the API answers 422 with a detail for each (API_STANDARDS §8). A help text or placeholder empty in both languages counts as none. References, cycles, keys and limits are checked at every save. Published versions always hold both languages, and only they reach an applicant, the public link, an application or an export.
- Copies from templates and previous projects copy both languages (BD-10).
- Snapshots keep the labels of their time: an application keeps its form version's labels and the workflow snapshot's stage names, so later renames never change old records (BD-12).

### 7.3 Rendering

- `localized(value, locale)` returns the requested language from a `Bilingual` object (or from a database row's `*_bn`/`*_en` pair on the server), falling back as in §8. The same helper serves screens, the worker and exports.
- API requests and responses carry configuration texts as the `Bilingual` object `{ bn, en }` (`components.schemas.Bilingual` in openapi.yaml, the same shape as the zod `bilingualText`); clients pick the language with `localized()`, so the same response serves both languages and offline caches stay valid after a language switch.
- Editing screens (form builder, project setup, reference lists, templates) show the two languages side by side for every text (SCR-060, SCR-061).
- Sorting by a bilingual name uses Bangla collation for bn (`Intl.Collator('bn')` on the client, the ICU collation `bn-x-icu` in PostgreSQL queries) and English collation for en.
- Search matches the text in the language and script the user typed; names typed by people are matched as typed (after NFC).

### 7.4 What is never translated

Beneficiary, volunteer and donor names, addresses, villages typed by users, comments, reasons, issue texts, stories and free-text answers. They are stored once, in the script they were typed, and shown unchanged in both interface languages.

## 8. Fallback rules

| Situation | Behaviour |
|---|---|
| Catalogue key missing in the user's language at runtime (should not happen: CI enforces parity) | Show the bn message; log the missing key once per process. In development the raw key is shown highlighted; in production a raw key is never shown |
| Catalogue key missing in bn too | Show the generic `common.state.error.text` message and log an error |
| Bilingual data value blank in the user's language (possible only in drafts) | Show the other language's value with a "translation missing" marker in editors; plain display without the marker for other users. The form builder and its preview print every text of a draft through `localized()`, so a question written in one language reads on the canvas, in the rule sentences, in the lists and in the change summary |
| Unsupported `Accept-Language` | Use the user's stored language, else `bn` |
| Future third language | The new locale, then `en`, then `bn`, for both catalogue keys and bilingual data |
| Notification template missing for the recipient's language | Not possible for bn and en (CI); for a third language fall back to `en` |

## 10. Fonts and rendering

Fonts, weights and the Bengali typography rules (no letter-spacing, no italics, line-height floors, wrapping instead of truncation) are defined in DESIGN_SYSTEM §2.4, §2.5 and §3. Since D-150 Public Sans draws Latin letters and all digits and Noto Sans Bengali draws Bengali (UbuntuSans and Bornomala until then), from one font stack in both languages, so switching language never changes fonts or digit shapes.

## 11. Adding a third language

No application code is rewritten; every step is configuration, data or an additive migration (NFR-44).

1. The owner records the decision in DECISION_LOG.md (language, script, direction, fallback).
2. Add the locale code to the list `L-locale` and to `SUPPORTED_LOCALES`; add its Intl locale tag with `-u-nu-latn` to the formatter (§6.1) and its day-period words if it uses 12-hour time.
3. Create `packages/shared/i18n/messages/<locale>/` by copying `en`; the catalogue check reports untranslated keys as warnings for this locale until it is complete, then as errors.
4. Generate an additive migration from `bilingual-columns.ts` that adds a nullable `*_<locale>` column to every listed table (with its hand-written down.sql, D-051); bn and en stay `not null`.
5. Translate bilingual data through the translation screen (`i18n.manage`); missing values fall back to en (§8).
6. Add notification templates for the new locale for every key and channel.
7. Add fonts for the script if Public Sans and Noto Sans Bengali do not cover it (DESIGN_SYSTEM §2.5), precache them, and embed them in PDF exports.
8. For a right-to-left script (for example Arabic or Urdu), set `dir="rtl"`; components already use CSS logical properties (`margin-inline-start`, `padding-inline-end`), which T1.4 adopts as the rule for all new CSS.
9. Run the full test suite in the new locale, including the 360 px screenshot set and the PDF snapshot.
