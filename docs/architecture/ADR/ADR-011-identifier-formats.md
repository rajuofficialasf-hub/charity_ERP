# ADR-011: Identifier formats (BEN-ID as UUID v7, application number per project)

Status: approved; derives from the owner's decision O-03 (2026-10-10). Written in task T0.22 (Phase 0 gate), where the ADR planned for T0.15 was found missing; the design itself has been in DATABASE_SCHEMA.md and ERD.md since T0.15 and T0.16.

## Context

The blueprint shows example ids (BEN-000123, APP-2026-00125, SBL-2026-00012) without a rule. People must find beneficiaries and applications reliably across years and projects; records are created offline on phones and synced later (BD-48), so ids cannot depend on a central counter at creation time. IDOR prevention (RBAC §8) requires that ids are not guessable sequences.

## Decision

- **Primary keys** of every table are UUID version 7 generated by the application (DATABASE_SCHEMA §2); PostgreSQL 17 has no native v7 generator, so there is no database default.
- **BEN-ID** is the beneficiary's UUID v7 itself (`beneficiaries.id`); there is no separate "BEN-" sequence. It is shown in full where an id is required (profile, merge pointer, exports); people find beneficiaries by NID or birth-registration number and name. A short display form needs a new decision (O-03).
- **Application number** is human-readable: project code + year + 5-digit sequence, for example `WNT-2026-00125`. The project code is set in project setup and is unique (proposed codes WNT, IFT, MEAT, QRB, SBL, HSE, SWT, TRP). The number is assigned by the server from the `id_sequences` counter when the application first reaches the server (offline drafts carry only their UUID and `client_uuid` until then).
- **Offline records** carry a `client_uuid` for idempotency (ADR-010); the server-side id and the application number are returned in the sync result.
- Retired BEN-IDs after a merge stay searchable and point to the kept profile (BD-05).

## Alternatives considered

- A "BEN-" plus 7-digit sequence for beneficiaries: easy to read aloud, but a central counter conflicts with offline creation and a sequential id invites enumeration; the owner chose UUID v7.
- Random UUID v4 everywhere: no time ordering, worse index locality for large tables.
- Application numbers without the project code: shorter, but the code tells staff at a glance which project an application belongs to.

## Consequences

Positive: ids can be created offline without collisions; UUID v7 keeps insert order and index locality; application numbers are readable on phones and in exports; ids do not reveal record counts.

Negative: the BEN-ID is long, so screens rely on NID and name for recognition; the application number exists only after the first sync, so offline lists show "pending number" for unsynced drafts.
