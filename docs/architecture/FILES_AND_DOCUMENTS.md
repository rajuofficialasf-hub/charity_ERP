Rules: a file may be linked to several entities (a distribution photo to the activity and the application); the link carries the slot that the workflow guards read (`photos.required_per_rule`, `evidence.photo_present`, `animal_photos.complete`); files are never hard-deleted except in the `exports` bucket (regenerable, BR-207); `sha256` is unique per project to stop identical re-uploads, while `phash` finds near-duplicates (section 6).

## 3. Access control

- No file is ever public and no URL to an object is ever issued (D-074, NS-41; D-108). Every download is `GET /api/v1/files/{id}/content` (with `variant` for the 320 px and 1,024 px thumbnails); the API runs the full request lifecycle (SYSTEM_ARCHITECTURE §6): the caller's permission on the record the file links to, its scope, the object-level check through the file's links, the sensitive-field class of the file kind (BR-183) and the scan state (section 5), then streams the object from the storage adapter (`apps/api/src/storage`; an S3 driver on MinIO until the NAS driver exists) with `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, the type taken from the stored bytes, and `inline` only for images and PDF (`attachment` otherwise, the original name encoded and never part of a key). A refusal answers 404.
- Who reaches a file linked to a record (T2.1, `apps/api/src/services/files.ts`): its uploader, and whoever holds a view permission of its kind whose scope reaches the record (`apps/api/src/files/records.ts`): photos through `application.view`, vouchers and payment copies through `application.review` or `budget.view` (never the Media Team), documents through `document.register.view`, and every kind through `file.upload`. To such a caller a file the scan has not cleared answers 423 `file.quarantined` (pending or failed) or 410 `file.infected`; `GET /files/{id}` shows its state and flags, the position only with `file.location` or to the uploader, and the near duplicate only when the caller reaches that file.
- The files of one record (`GET /files?entityType=&entityId=`, T2.1): the kinds whose view permission reaches the record and the caller's own uploads to it, the latest upload start first (the time-ordered file id), by cursor; kind, slot, type, size, capture time, upload time, scan state and flags, the position row by row (with `file.location`, or on the own uploads), never a key, a name or free text. `format=csv` gives the same columns for at most 5,000 rows as a download; every export is audited as `file.list_exported`, and a list or export with NID photos as `file.nid_viewed`.
- The MinIO endpoint is reachable only by the API on the internal network; its admin API and bucket listing are never reachable from outside (D-056).
- Views of sensitive classes write an audit entry: a NID photo `file.nid_viewed`; a file list or CSV export of a record `file.list_exported`, and `file.nid_viewed` when it holds NID photos (BR-179, BR-224).
- Uploads go through the API in 256 KB parts (section 4); the client never holds storage credentials or a storage URL.
- The GPS position of a file is the field class `file.location`: officials doing the project's work and the uploader see it; volunteers see their own files only; the Media Team receives media assets and consent state, never NID photos or vouchers (sensitive_fields catalogue in `permissions.yaml`).

## 4. Upload pipeline

```
client                                     api                                         minio / worker
 1 POST /upload-sessions ──────────────►  policy check: kind allowed for the record type, declared type
   { kind, entityType, entityId, slot,    and size per section 5, project photo_source setting (section 7),
     mime, size, sha256, captured_at,     at most 20 open sessions per user; permission file.upload and
     gps, source, client_uuid }           the caller's scope over the record (404 out of reach)
 2 ◄── session { id, chunk_size 256 KB, part_count, parts_received, expires 1 h after the last part }
 3 PUT /upload-sessions/{id}/parts/{n} ─►  part ≤ 256 KB, n inside the declared size ──►  multipart part
   (resumable: GET /upload-sessions/{id} returns the parts held after a drop; a held part sent again
    answers the same; bytes received never pass the declared size)
 4 POST …/finalize ────────────────────►  the record's scope checked again; complete multipart; verify
                                          size and sha256; read magic bytes;
                                          write files row (virus_scan pending, flags from metadata);
                                          link to entity; enqueue photos job; return file id + flags
 5                                                        photos job (worker): virus-scan hook, EXIF read
                                                          (server-side confirmation), thumbnails 320 px and
                                                          1,024 px (PROPOSAL), phash, duplicate check,
                                                          flag updates, re-evaluate workflow guards
```

- The offline photo queue (OFFLINE_SYNC §5) uses exactly this pipeline; a photo uploads only after its owning record has a server id, text first, photos later.
- **The public path** (the public application link, T2.3): an applicant with no login sends each photo in one request to `POST /public/forms/{token}/photos?clientUuid=…&fieldKey=…` (JPEG or PNG up to 5 MB, the `public-form` rate class, the `form_photo` kind), the same way a registration photo goes: type by magic bytes, metadata stripped, stored in the `photos` bucket under `public/<hash of the token>/<client id>/<file id>`, a `files` row with no uploader and the project of the link, the processing job queued. Until the submission arrives the photo's `file_links` row names the pending submission (`entity_type = public_submission`, `entity_id` = the client id, `slot` = the field key), an entity the file routes never resolve, so nobody can read it. At most 5 photos per client id (the sixth answers 429 `public.photo_limit`) and at most 200 unclaimed photos or 500 MB per link (429 `public.link_full` with `Retry-After` until a claim or the sweep frees room); the same bytes twice are stored twice (the identical-file index of a project leaves form photos out, so the public is never told that a picture already exists on the project). The submission names the photos in its `photo` answers; the service re-points their links to the application (a photo of another client id or link answers 422 `public.photo_unknown`), after which an official who reaches the application reads them like any evidence photo. The nightly upload sweep removes the photos no submission claimed within 24 hours through `purge_unclaimed_public_photos` (the rows, then the objects and thumbnails).
- A session that is not finalized within its expiry is aborted by a nightly sweep, which also removes its stored parts; an interrupted upload resumes from the parts the server holds (NFR-24).
- Finalize is idempotent on `client_uuid` + slot: a repeated finalize returns the existing file (200 with `Idempotent-Replay: true`, as a resent create returns its session).
- Records a chunked upload links to, and the kinds each takes (`@css/shared/files`, T2.1): application (distribution, construction and evidence photos, voucher, payment copy), activity (the three photo kinds), issue (issue photo), voucher (voucher), expense claim (voucher), payment (payment copy), animal (animal photo), document (document). Profile and NID photos keep the registration upload (D-087); beneficiary photos and media assets come with their modules. Any other pair answers 422 `file.kind_not_allowed`.
- Who reaches a record (RBAC.md 8): a global, program or project grant of `file.upload` reaches every record of the project; an area grant the records of its place (an application's region, district, upazila or union, or of the application the record belongs to) and project-wide records; SELF the caller's own records (the application's owner volunteer or creator, the issue's raiser, the voucher's submitter, the claim's volunteer, the animal's volunteer, the creator otherwise) on a project the caller works on. ASSIGNED reaches nothing until the work assignments exist; the Media and Procurement Teams' `own_part` grants likewise. A project takes files while active or closing (409 `project.read_only` otherwise).
- The flags the declaration decides are set at finalize for photos (`no_capture_time`, `no_gps`, `stale_capture` against the record's own device time where it keeps one, or a capture after the server received the photo, and `gallery_under_camera_only` against the project's photo source); the processing job sets them again after reading the photo's own metadata.
- The processing job (T2.1, `apps/api/src/jobs/file-process.ts`) runs on the `photos` queue, enqueued in the finalize transaction once per file: the virus scan (`failed` and a retry when the scanner fails, `infected` for good); for a photo, a header check that refuses a canvas over 40 megapixels or another format before any pixel is decoded (the file ends `failed`); the capture time from EXIF wins over a declared one (a declared time more than ten minutes from it sets `stale_capture`), the position from EXIF fills one the phone did not declare; the 320 px and 1,024 px JPEG thumbnails beside the object in `thumb/`; the 64-bit difference hash and `duplicate_suspect` on both files of a near duplicate in the same project. A processed file is left alone, so a repeated job changes nothing.

The exception of D-087 (2026-10-12) ended with T2.1: the registration and profile photos are queued for the processing job when they are uploaded, the photos stored before are queued when the consumers start, and like every file they are viewable only once the scan cleared them (`skipped` outside production). Identity photos carry no data-quality flags.

Scan policy (O-30, BR-239): **every uploaded file stays quarantined until the security scan succeeds.** While `virus_scan = pending` the file's metadata row and its link exist (so the workflow knows a photo was attached and the volunteer sees "processing"), but the file cannot be previewed, downloaded, thumbnailed into any response or placed on the publishable list; `scan_pending` is a processing flag only, never a permission. An infected result blocks the file permanently (`virus_scan = infected`): links are hidden, the uploader and the Monitoring Team get an immediate alert (`security.malware_detected`), and the record's photo guard counts the file as absent. A scanner failure or timeout (`scan_failed`) is never treated as clean: the file stays quarantined, the scan is retried by the worker, and repeated failures raise an operations alert. Workflow guards that need photos (`photos.required_per_rule`, `evidence.photo_present`, `animal_photos.complete`) count only files with `virus_scan = clean`, so a step cannot complete on unscanned files; in dev/test the scan adapter answers "clean" synchronously so flows are not blocked, while staging and production use the ClamAV daemon.

Rejections return i18n error codes (`file.type_not_allowed`, `file.too_large`, `file.source_not_allowed`); nothing is silently dropped.

## 6. Image handling

- **Client-side compression**: before a photo enters the device queue it is resized to at most 1,600 px on the longest edge and encoded to JPEG at quality about 80 (WebP where supported), targeting ≤ 300 KB (NFR-25). Capture time and GPS are read **before** compression and sent as explicit metadata in the initiate call, because re-encoding may strip EXIF.
- **Server-side**: the compressed image is stored as the original (no re-encode); the worker produces two thumbnails (320 px for lists, 1,024 px for the verification view and PDF exports, both preserving the aspect ratio; O-30), reads EXIF if present to confirm the client metadata, and computes a 64-bit perceptual hash.
- **Timestamps (O-30)**: three times are stored separately: `captured_at` (device clock at capture), `record_created_at` (the owning activity or application's `client_created_at`) and `uploaded_at` (server receipt). `stale_capture` is set when `captured_at` and `record_created_at` differ by more than 10 minutes, which catches an old photo attached to today's work. A late `uploaded_at` caused by offline operation never triggers the flag on its own.
- **Duplicate detection (BD-21, BR-109, O-30)**: identical bytes (`sha256`) within a project are rejected as a repeat upload with a message, under the project-level deduplication policy (the PM may relax it for kinds where identical files are legitimate, e.g. the same voucher attached to two claims); near-duplicates (pHash Hamming distance ≤ 6 within the same project) set `duplicate_suspect` on both files and show a warning on the record and in the officials' verification view with the other photo side by side. Duplicate detection **warns but never blocks**: the volunteer may keep the photo with a note; the official decides. The threshold is validated against representative project images before the Phase 3 pilot (T3.1) and is an admin setting.
- **Capture time and GPS**: `captured_at` comes from the in-app camera (device clock at the moment of capture) or from EXIF for file-input captures; GPS from the Geolocation API at capture time with the user's permission, with accuracy stored. Missing values set `no_capture_time` / `no_gps`. Flags are shown as badges (UX-07 verification view: photo, time, place, source, flags) and are available to monitoring; they never block submission or completion by themselves (BD-21 requires photos per the photo rule; it does not require unflagged photos) — this is a deliberate design choice so that field work on phones without GPS fix is not stopped, while officials see exactly what is missing.

How "camera only" is realised on the web:

| Approach                                    | How                                                                                                                                                                | Guarantees                                                                                                   | Trade-offs                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| In-app capture (primary on Android Chrome)  | `getUserMedia` with the rear camera in an in-app camera screen; capture button writes the frame to a canvas, compresses, records device time and GPS fix, enqueues | Capture time is the moment of the tap; gallery selection impossible; GPS requested at capture; works offline | Needs camera permission; on 2 GB Android phones the preview must be low resolution (720p) to avoid memory pressure; some WebViews lack `getUserMedia`; iOS Safari supports it only in the installed PWA and Safari tab, not in in-app browsers; battery and heat on long distribution days → the screen releases the stream between captures |
| Device camera through file input (fallback) | `<input type="file" accept="image/*" capture="environment">`; the OS camera app opens                                                                              | Reliable on every platform including iOS and low-RAM phones; EXIF usually present                            | Browsers may still let the user pick from the gallery (the `capture` attribute is a hint); EXIF may be stripped by the OS; GPS depends on the OS camera's settings → the server relies on flags (below) rather than on a guarantee                                                                                                           |
| Gallery (only when camera_or_gallery)       | plain file input without `capture`                                                                                                                                 | Lets the volunteer attach existing vouchers and paper photos                                                 | Capture time comes from EXIF if present; `source=gallery` recorded                                                                                                                                                                                                                                                                           |

Policy: when the project says `camera_only`, the app shows only the in-app camera where available and the `capture` file input otherwise; the initiate call declares `source`. The server flags a file as `gallery_under_camera_only` when the declared source is gallery, and `stale_capture` per section 6 (capture time more than 10 minutes away from the record's creation time; a late upload alone never flags), covering the "old photo re-used" case of A8.1. Flags are visible to officials and to monitoring; they do not block (section 6).

Flagged-photo monitoring (O-30, BR-241): the data-quality flags that count are `no_capture_time`, `no_gps`, `gallery_under_camera_only`, `stale_capture` and `duplicate_suspect`; `scan_pending`, `scan_failed` and infected results are security states, not data-quality flags. The `alerts` job raises `photo.flagged_share` when, for a volunteer within a project, more than 30% of photos carry at least one data-quality flag and the sample is at least 20 photos (minimum sample size, admin-editable like the threshold; every change to either value is audited). Malware and other critical security findings never wait for this job: they raise separate immediate alerts (section 5).

## 10. Deadlines, soft warning and non-compliance (SOP clause 6, BD-36)

- Working days (O-16): every day except Friday and the dates in the admin holiday calendar. The `alerts` job runs daily after midnight Asia/Dhaka.
- At `due_at` passed and status before `collected`: a **soft warning** notification goes to the responsible official (in-app and email) and a 3-working-day countdown starts (`warning_sent` event).
- When the countdown ends and the document is still not collected: `non_compliant_at` is set, the document and the official appear in the monitoring control centre (alert `document.overdue`), and the project's document compliance rate reflects it (BR-166). Later submission clears the overdue alert but keeps the non-compliance record for the quarterly report.
- Extension: the PM may extend `due_at` with a reason (`document.deadline.extend`), audited (BR-171); an extension before the deadline prevents the warning; an extension during the countdown stops it.
- Non-compliance never touches volunteer ratings or categories (BD-36): the register has no volunteer actors.

## 12. Quarterly audit report (SOP clause 13, BD-39)

One click (`document.audit.run`) produces a PDF and a CSV for a quarter and a scope (program/project/district): pending documents by project and responsible official, on-time submission rate, warnings and non-compliance counts, deficiency summary (new, escalated, legacy), hard copies past the 5-year retention, documents without a hard-copy code. Generated by the export job, stored under `exports`, downloaded through the API, which streams it; the generation is audited.

The register also exports its full columns to Excel/CSV, replacing the SOP tracking sheet (BR-169).

## 13. Media consent and the publishable list (SOP clause 12, BD-38, O-17, O-28)

- `media_consents` (beneficiary_id, granted, channels[], recorded_at, recorded_by, evidence_file_id nullable, revoked_at) is recorded by an official on the beneficiary profile (`beneficiary.consent.record`); the channel list (website, Facebook, print, video, donor report) is admin-editable (O-17).
- A file enters the **publishable list** (`media.publishable.manage`) only when its beneficiary has an active consent covering the requested channel; the list item stores `consent_channels_at_publish`. Revocation removes items from the list for future use but keeps the history and what was already published, with the revocation date visible.
- The Media tab (O-28) shows the consent state next to each beneficiary on the media work list; assets of beneficiaries without consent are visible to the Media Team for planning but marked "not publishable".
- Media assets never include NID photos or vouchers; the Media Team's file access is limited to `media` bucket assets and distribution photos of beneficiaries on its work list (section 3).

## 14. Locks, retention and storage growth

- **Locks**: `locked_at` is set on vouchers and evidence photos when an official verifies them (BR-122, BR-123; effect `lock:vouchers`, `lock:photos`) and on every project file at project close; a locked file cannot be replaced or unlinked; new files may still be added where the workflow allows (e.g. follow-up photos after close). Only the Monitoring Team's merge revert may re-link locked files (BD-05).
- **Retention**: permanent for every business file (BD-46, BR-207); the `exports` bucket is the only one with deletion; soft delete (`deleted_at`) exists only for exports.
- **Storage growth** (BD-46, NFR-30, SYSTEM_ARCHITECTURE §11): the nightly `storage-stats` job records bytes and object counts per bucket and per project, plus database size; the admin screen shows growth per month and the projected date for the configured disk threshold; a monthly summary email goes to the IT team; crossing the threshold raises a monitoring alert. Built in T2.1 (`apps/api/src/jobs/storage-stats.ts`, 02:15 Dhaka, one snapshot a day): the rows per bucket and project, and on the system health page each bucket with its files, bytes and growth since the snapshot of at least 30 days ago; the database size, the projected date, the monthly email and the threshold alert come with the monitoring module.
- **Backups**: all buckets except `exports` mirrored per O-06; restore drill includes a sample of documents and photos with their metadata rows.
