# DATABASE SCHEMA AND DATA DICTIONARY (PostgreSQL 17)

Status: complete, task T0.16 (2026-10-10); implemented in T1.2 (2026-10-11) as `apps/api/prisma/schema.prisma` and the initial migration `apps/api/prisma/migrations/20261011000000_init/` with a hand-written `down.sql` (ADR-003); seeds follow in T1.3. This dictionary is the physical form of `docs/database/ERD.md` (91 tables: the 90 entities of T0.15 plus `id_sequences`); every table, column, constraint and index here must appear in the migrations, and a change here is a change there in the same commit (PROJECT_RULES §5). JSON Schemas for JSONB columns: `docs/database/json-schemas/`. The proposals of the first draft were accepted by the owner on 2026-10-10 (O-38, O-39); where the text says PROPOSAL the value is decided as listed in section 24.

Note on human ids: the T0.16 prompt mentions "BEN-" ids "per DECISION_LOG". DECISION_LOG O-03 decided that the BEN-ID **is** the beneficiary's UUID v7; there is no `BEN-` sequence. Only applications carry a human id. This dictionary follows O-03.

## 1. Scope and how to read it

Each table section lists its columns (type, null, default, comment), then its keys, unique constraints, check constraints, foreign keys and indexes. `[A]` stands for the four audit columns of section 3; `[L]` for the two log columns. Code lists (allowed values of `text` columns) are defined once in section 5 and referenced by name, e.g. `CHECK code list L-app-status`.

## 2. Naming and type conventions

| Topic | Rule |
|---|---|
| Names | snake_case; plural table names; FK columns `<entity>_id`; booleans `is_*`/`has_*` or plain adjectives (`active`, `enabled`); timestamps `*_at`; dates `*_on` or explicit (`due_at` is a timestamp, `apply_from` a date) |
| Primary keys | `id uuid` UUID version 7, generated by the application (PostgreSQL 17 has no native v7 generator; 18 adds one, not relied on); no database default. Natural-key tables: `roles.key`, `permissions.name`, `settings.key`, `holiday_calendar.date`, `id_sequences.scope_key`, `distributions.activity_id` |
| Text | `text` with CHECK length limits where a limit matters (codes ≤ 64, names ≤ 200, comments ≤ 4,000); no `varchar(n)` |
| Money | `numeric(14,2)`, BDT, CHECK ≥ 0 unless a signed ledger amount |
| Counts and scores | `integer` or `smallint` with CHECK ranges |
| Time | `timestamptz` stored in UTC (`*_at`); business dates as `date` interpreted in Asia/Dhaka |
| GPS | `latitude numeric(9,6)`, `longitude numeric(9,6)`, `gps_accuracy_m numeric(7,2)`; no PostGIS dependency (PROPOSAL) |
| Bilingual configuration | `name_bn`, `name_en` (or `label_bn`, `label_en`, `title_bn`, `title_en`) both `not null` |
| Lists of codes | `text[]` with a CHECK that every element is in the code list when the list is fixed |
| JSONB | only where section 20 lists it; every JSONB column has a JSON Schema and the matching zod schema in `packages/shared` |
| Enums | **No PostgreSQL ENUM types.** Fixed system codes are `text` + CHECK (section 5.1); configurable lists are rows in `reference_lists` (section 5.2) or per-project data validated by the service (section 5.3) |

## 3. Audit columns and the system actor

`[A]` = these four columns on every business table:

| Column | Type | Null | Default | Comment |
|---|---|---|---|---|
| created_at | timestamptz | no | now() | UTC insert time |
| created_by | uuid | yes | — | FK users(id); null only when the seeded system actor is not yet available during seeding; jobs act as the system user |
| updated_at | timestamptz | no | now() | set by the application on every update (and by a `set_updated_at` trigger as a backstop) |
| updated_by | uuid | yes | — | FK users(id) |

`[L]` = log tables: `created_at timestamptz not null default now()`, `created_by uuid null references users(id)`. A BEFORE UPDATE OR DELETE trigger protects them (O-46 item 9; scope decided in D-060, implemented and tested in T1.2):

| Kind | Tables | Rule |
|---|---|---|
| Strict append-only | audit_log, budget_ledger, stock_movements, document_events, application_transfers, volunteer_categories_log, workflow_transitions | every UPDATE and DELETE raises an error |
| Status log | device_sessions, otp_codes, upload_sessions, notifications, outbound_messages, push_subscriptions, field_changes | DELETE raises an error; UPDATE may change only the columns listed in D-060 (for example `notifications.read_at`, the worker's delivery columns of `outbound_messages`, `field_changes.unlock_state`) |

Expired `otp_codes` and unfinalized `upload_sessions` may be deleted only by the cleanup jobs, which set the session setting `css.cleanup = on` (section 21).

The **system actor** is a fixed `users` row (`kind = 'system'`, state `active`, cannot log in) used as `created_by` for job-written rows; the originating user is kept in the row (for example `audit_log.actor_user_id`) when a job acts for someone (SYSTEM_ARCHITECTURE §6).

## 4. Human ids and the counter table (O-03)

| Id | Format | Generation |
|---|---|---|
| Beneficiary (BEN-ID) | the UUID v7 `beneficiaries.id` | application-generated; shown in full where an id is required (profile, merge pointer, exports); a short display form needs a new decision (O-03); search uses NID/birth number and name |
| Application number | `{project.code}-{year}-{5-digit sequence}`, e.g. `WNT-2026-00125` | server-side, inside the transaction that creates the server row: `UPDATE id_sequences SET last_value = last_value + 1 WHERE scope_key = 'app:'||project_id RETURNING last_value` (row lock serializes concurrent creations; a rollback undoes the increment, so committed numbers have no gaps); the row is created with `last_value = 0` when the project is created |
| Offline records | no `app_no` until synced | the device shows a short client reference (last 6 characters of `client_uuid`); the server assigns `app_no` at sync |
| Project code | 2–8 uppercase letters, unique (`WNT`, `IFT`, `MEAT`, `QRB`, `SBL`, `HSE`, `SWT`, `TRP`, …) | entered by the PM in project setup (O-03) |

Deactivating a code (`active = false`) keeps old rows valid; the service refuses inactive codes for new rows.

### 5.3 Per-project lists (validated by the service against the project snapshot)

Beneficiary class options (BD-14; defaults from `reference_lists` `beneficiary_class_default`), expense categories (O-14), issue types, outcome labels, stage keys, application statuses beyond the common ones, follow-up questions. They are copied into a project with its template and can be edited per project (BR-065, BR-079), so a database FK to one global list would be wrong. Columns store the code (`class_code`, `category_code`, `type_code`, `stage`, `outcome`), and the service validates them against `projects.workflow_snapshot` and `project_components.settings` on every write; reports join labels from the same snapshot.

`reference_lists` also holds the **defaults** for these lists (`beneficiary_class_default`, `expense_category_default`, `issue_type_default`) used when a template is created. Seed values (T1.3): beneficiary classes of BD-14, expense categories of O-14, issue types of O-53.

## 18. BD-03: beneficiary mobile must not be the submitting volunteer's mobile

Enforcement in two layers (BR-008):

1. **Service** (friendly error first): when an application is created, linked or edited, and when a beneficiary's mobile changes, the application service compares the beneficiary mobile with the owner volunteer's `users.mobile` and with the creating user's mobile; on match it returns the validation error `beneficiary_mobile_is_volunteer_mobile` with the field.
2. **Database backstop**: one PL/pgSQL function `check_beneficiary_mobile_not_volunteer(application_id)` raising SQLSTATE `23514` with the message key, called by three **constraint triggers** (`DEFERRABLE INITIALLY DEFERRED`, so multi-row transactions are checked at commit):
   - `applications` AFTER INSERT OR UPDATE OF beneficiary_id, owner_volunteer_id, created_by_user_id, status — for the row, when status <> 'deleted';
   - `beneficiaries` AFTER UPDATE OF mobile — for every non-deleted application of that beneficiary;
   - `users` AFTER UPDATE OF mobile — for every non-deleted application owned or created by that user.

   The check: `beneficiaries.mobile` equals `users.mobile` of the owner volunteer's user, or of `created_by_user_id`. Public-link applications (no owner, no creator) are not checked.

Rationale for triggers rather than a CHECK: the two values live in different tables; PostgreSQL CHECK constraints cannot reference other rows. Tests (T2.2): direct SQL insert violating the rule fails; service path returns the friendly error; mobile change on either side is caught.

## 21. Soft delete policy

- Nothing of business value is hard-deleted (constitution §2, BR-207). The application database role has **no DELETE privilege** on business tables.
- Allowed "deleted" states: `applications.status = 'deleted'` with `deleted_at` (only drafts and pending applications, by the owner or an official with the permission; BR-091); `files.deleted_at` only for `kind = 'export'` (regenerable).
- Ending instead of deleting: `revoked_at` (roles, permissions, sessions, push subscriptions), `ended_at` (project staff and volunteer assignments), `removed_at` (team members), `released_at` (blocklist), `active = false` (locations, reference lists, templates, programs), `deactivated_at` (users), `reverted_at` (merges).
- Technical rows the system may delete: expired `otp_codes`, expired unfinalized `upload_sessions`, export files after 30 days (O-30), expired unsubmitted `registration_drafts` with their photo `files` rows (D-082). These deletions are performed by jobs running under a dedicated role with DELETE only on those tables; the drafts and their photos only through the `SECURITY DEFINER` function `purge_expired_registration_drafts`, so the role has no DELETE on `files`.

## 22. Retention, partitioning and archiving

- **Retention** is permanent for all business data, logs, photos and documents (BD-46). Storage growth is reported nightly (`storage_stats`).
- **audit_log**: declarative RANGE partitioning by month on `created_at` from the first migration (PROPOSAL; cheap now, very costly to retrofit). A monthly job creates the next partitions ahead of time. Old partitions are never dropped; they may be moved to a slower tablespace and become read-only. Queries by entity or person use per-partition indexes; the viewer always filters by a date range to prune partitions.
- **notifications, outbound_messages, field_changes**: start unpartitioned; convert to monthly partitions when a table exceeds about 20 million rows or 20 GB (PROPOSAL threshold), watched through `storage_stats`.
- **files**: not partitioned; rows are small and the bytes live in MinIO; object storage growth is the concern and is reported per bucket and project.
- **application_answers**: not partitioned; indexed by application; expected to stay within tens of millions of rows over many years.
- **Archiving**: no archive deletion. Closed projects stay in the same tables (read-only by the workflow guards); reports filter by year. Backups and restore drills follow O-06 (RPO 24 h → 1 h with WAL, RTO 4 h, monthly drill).
