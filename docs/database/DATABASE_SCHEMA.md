Status: complete, task T0.16 (2026-10-10); implemented in T1.2 (2026-10-11) as `apps/api/prisma/schema.prisma` and the initial migration `apps/api/prisma/migrations/20261011000000_init/` with a hand-written `down.sql` (ADR-003); seeds follow in T1.3. JSON Schemas for JSONB columns: `docs/database/json-schemas/`. The proposals of the first draft were accepted by the owner on 2026-10-10 (O-38, O-39); where the text says PROPOSAL the value is decided as listed in section 24.

Note on human ids: the T0.16 prompt mentions "BEN-" ids "per DECISION_LOG". DECISION_LOG O-03 decided that the BEN-ID **is** the beneficiary's UUID v7. Since T2.2 (D-112) every profile also has a short sequential number `ben_no`, shown as `BEN-0000123`, from the sequence `beneficiaries_ben_no_seq`; the UUID stays the key and the merge pointer. Applications carry their own human id.

## 1. Scope and how to read it

Each table section lists its columns (type, null, default, comment), then its keys, unique constraints, check constraints, foreign keys and indexes. `[A]` stands for the four audit columns of section 3; `[L]` for the two log columns. Code lists (allowed values of `text` columns) are defined once in section 5 and referenced by name, e.g. `CHECK code list L-app-status`.

## 2. Naming and type conventions

| Topic | Rule |
|---|---|
| Names | snake_case; plural table names; FK columns `<entity>_id`; booleans `is_*`/`has_*` or plain adjectives (`active`, `enabled`); timestamps `*_at`; dates `*_on` or explicit (`due_at` is a timestamp, `apply_from` a date) |
| Primary keys | `id uuid` UUID version 7, generated by the application (PostgreSQL 17 has no native v7 generator; 18 adds one, not relied on); no database default. Natural-key tables: `roles.key`, `permissions.name`, `settings.key`, `holiday_calendar.date`, `id_sequences.scope_key`, `distributions.activity_id` |
| Text | `text` with CHECK length limits where a limit matters (codes ≤ 64, names ≤ 200, comments ≤ 4,000); no `varchar(n)` |
| Money | `numeric(14,2)`, BDT, CHECK ≥ 0 unless a signed ledger amount |
| Counts and scores | `integer` or `smallint` with CHECK ranges |
| Time | `timestamptz` stored in UTC (`*_at`); business dates as `date` interpreted in Asia/Dhaka |
| GPS | `latitude numeric(9,6)`, `longitude numeric(9,6)`, `gps_accuracy_m numeric(7,2)`; no PostGIS dependency (PROPOSAL) |
| Bilingual configuration | `name_bn`, `name_en` (or `label_bn`, `label_en`, `title_bn`, `title_en`) both `not null`; a text of a form draft may hold the empty string in a language until its version is published (I18N.md §7.2, D-171) |
| Lists of codes | `text[]` with a CHECK that every element is in the code list when the list is fixed |
| JSONB | only where section 20 lists it; every JSONB column has a JSON Schema and the matching zod schema in `packages/shared` |
| Enums | **No PostgreSQL ENUM types.** Fixed system codes are `text` + CHECK (section 5.1); configurable lists are rows in `reference_lists` (section 5.2) or per-project data validated by the service (section 5.3) |

## 3. Audit columns and the system actor

`[A]` = these four columns on every business table:

| Column | Type | Null | Default | Comment |
|---|---|---|---|---|
| created_at | timestamptz | no | now() | UTC insert time |
| created_by | uuid | yes | — | FK users(id); null only when the seeded system actor is not yet available during seeding; jobs act as the system user |
| updated_at | timestamptz | no | now() | set by the application on every update (and by a `set_updated_at` trigger as a backstop) |
| updated_by | uuid | yes | — | FK users(id) |

`[L]` = log tables: `created_at timestamptz not null default now()`, `created_by uuid null references users(id)`. A BEFORE UPDATE OR DELETE trigger protects them (O-46 item 9; scope decided in D-060, implemented and tested in T1.2):

| Kind | Tables | Rule |
|---|---|---|
| Strict append-only | audit_log, budget_ledger, stock_movements, document_events, application_transfers, volunteer_categories_log, workflow_transitions | every UPDATE and DELETE raises an error |
| Status log | device_sessions, otp_codes, upload_sessions, notifications, outbound_messages, push_subscriptions, field_changes | DELETE raises an error; UPDATE may change only the columns listed in D-060 (for example `notifications.read_at`, the worker's delivery columns of `outbound_messages`, `field_changes.unlock_state`) |

Expired `otp_codes` and unfinalized `upload_sessions` may be deleted only by the cleanup jobs, which set the session setting `css.cleanup = on` (section 21).

The **system actor** is a fixed `users` row (`kind = 'system'`, state `active`, cannot log in) used as `created_by` for job-written rows; the originating user is kept in the row (for example `audit_log.actor_user_id`) when a job acts for someone (SYSTEM_ARCHITECTURE §6).

## 4. Human ids and the counter table (O-03)

| Id | Format | Generation |
|---|---|---|
| Beneficiary (BEN-ID) | the UUID v7 `beneficiaries.id` | application-generated; shown in full where an id is required (profile, merge pointer, exports); a short display form needs a new decision (O-03); search uses NID/birth number and name |

### 5.3 Per-project lists (validated by the service against the project snapshot)

Beneficiary class options (BD-14; defaults from `reference_lists` `beneficiary_class_default`), expense categories (O-14), issue types, outcome labels, stage keys, application statuses beyond the common ones, follow-up questions. They are copied into a project with its template and can be edited per project (BR-065, BR-079), so a database FK to one global list would be wrong. Columns store the code (`class_code`, `category_code`, `type_code`, `stage`, `outcome`), and the service validates them against `projects.workflow_snapshot` and `project_components.settings` on every write; reports join labels from the same snapshot.

`reference_lists` also holds the **defaults** for these lists (`beneficiary_class_default`, `expense_category_default`, `issue_type_default`, `application_kind_default`) used when a template or a project is created. Seed values (T1.3): beneficiary classes of BD-14, expense categories of O-14, issue types of O-53; the application kinds of open-application projects (educational institution, personal garden; T1.11, D-095).

Constraints: UNIQUE (nid) WHERE nid IS NOT NULL; UNIQUE (birth_reg) WHERE birth_reg IS NOT NULL (BR-003); CHECK merged_into_id <> id. The database asks for no document and no mobile (D-172, BR-298, BR-299; migration `20261112160000_beneficiary_optional_identity` dropped the CHECK `beneficiaries_identity_check` and the NOT NULL of `mobile`): a profile without a document has neither number, and whether an application must carry a document or a mobile is its project's rule, held by the service (BR-001, BR-297). A number that is given keeps its format CHECK and its uniqueness; every comparison of a mobile (the format CHECK, the own-mobile triggers of section 18, the duplicate and family queries) uses `=` or `~`, which is never true for NULL, so a missing number is refused by none of them and pairs with nobody. Rollback of that migration (its `down.sql`): on a database where no profile lacks a document or a mobile and no application has the kind `none`, the earlier schema returns exactly; where such rows exist they stay, `mobile` stays nullable in its type (PostgreSQL cannot set NOT NULL on a column that holds a NULL) and the three rules return as CHECK constraints NOT VALID (`beneficiaries_mobile_required`, `beneficiaries_identity_check`, `applications_identity_kind_check`), which hold every new and every changed row and leave the existing ones. A kept row is therefore frozen: PostgreSQL holds a NOT VALID check against every new version of a row, so such a profile or application refuses every update (a block, a merge, an address change, a move to another state) until it is given its document and its mobile (the application: a kind of `nid` or `birth_reg`) or the check that holds it is dropped by hand; the script ends with a WARNING that counts the kept rows. It must be run in one transaction (`psql --single-transaction -f down.sql`), can be run again, and applying the migration again removes the stand-in checks. Adding the stored generated column `mobile_owner_list` rewrites the table once. The name keys (D-174, BR-301; migration `20261114120000_beneficiary_name_keys`): two spellings of one person's name compare equal through a key made from the name as written, which is always kept and shown. The key drops a known title only where it stands (at the start, any number in a row: মোঃ, মো., মোহাম্মদ, মুহাম্মদ and their short forms মোহাঃ, মোহা., মুহাঃ, মুহা., মোছাঃ, মোসাঃ, মোসাম্মৎ, হাজী, আলহাজ্ব, শ্রী, শ্রীমতি and their Latin forms; at the end: বেগম, খাতুন), keeps every word that can be a family name (শেখ, মুন্সী), removes spaces and punctuation, folds Unicode NFC, invisible joiners and Latin letter case, makes no letters equal (শ, ষ and স stay apart), and maps each word through the spelling variants of the groups switched on (`name_variant_groups`, `name_variants`; a group spelling that is itself a variant of another group is followed to the end of the chain, and a chain that comes back to itself ends at its smallest spelling). The keys are computed once, in TypeScript, and stored: an editable list cannot feed an immutable SQL function, so there is no SQL twin and no expression index (the older `person_name_key` stays for the search; the duplicate pairs, the family signals and the comparison with the block list read these columns). Every write of a name, a father's or husband's name or a village stores the keys with `match_keys_version` in the same transaction (`services/match-keys.ts`: a new profile, a decided correction of a name, a contact change of the village, a merge and its revert for both profiles). The migration computes nothing: on the field's table (2,000,000 rows in the measurement data set) that would hold the migration for minutes, so the columns arrive empty and the key job `jobs/name-keys.ts` on the `name-keys` queue fills them: queued when the worker starts and finds a row without current keys, queued in the transaction that raises the list's version, and nightly at 02:30 Dhaka time. One run at a time: the queue has the pg-boss policy `stately` (one job waiting, one running) and every place that queues it gives the singleton key `name-keys`. It walks each table by id in batches of 2,000 rows, each in its own transaction, locking its rows in id order as it reads them, writes a row only while its keys are older than the list and its names and village are still the ones the keys were computed from (so it never overwrites a newer write, and a second run writes nothing), and marks its transactions with `css.match_keys_only = on`: the update-stamp trigger of the two tables (`set_updated_at_unless_match_keys`) then keeps `updated_at` as it was, so a key write moves no profile's "last changed" and makes no official's open edit stale. A write that read the version just before the list changed stores the older version; the job queued by the change or the nightly one computes that row again. Indexes for the pair queries: (union_id, name_key, guardian_key) and (union_id, village_key), both WHERE merged_into_id IS NULL. Index of the keys to compute: (match_keys_version), which holds the NULLs too, so it serves both the missing and the older keys; the check at the worker's start asks each of the two in a probe of its own, so each is a condition of the index, with a statement time limit of a minute, and a failed or timed-out check is logged as an error and queues the job anyway. The migration builds its indexes with a plain CREATE INDEX, which holds the writes to the table while it builds (docs/ops/DEPLOYMENT.md, section 5). The rollback (`down.sql`) drops the columns, the three tables, the indexes and the trigger function and gives both tables the plain `set_updated_at` trigger again; the keys are derived, so nothing a person wrote is lost.

The times helped (D-172, BR-307; migration `20261115120000_beneficiary_help_counters`): the beneficiary list shows `help_count`, filters on `max_helps_in_year > 1` and orders by `help_count`, over every live profile, so the two are kept on the row instead of counted per request; the profile's own summary and an application's `helpedBefore` are always counted live from the applications, never read from here. Which applications count is the one shared rule (`countsAsHelped` of `@css/shared`, read in SQL by `helpedSql` of `apps/api/src/services/help-history.ts`), over the same set as the profile: the person's own applications and the ones each live merge left on its retired profile (`snapshot.leftBehind`), which count for the kept profile and for every profile that one was later retired into. A retired profile keeps the count of what still sits on it, its left-behind applications; the list never shows it. CHECK `beneficiaries_help_counts_check`: both are at least 0 and `max_helps_in_year <= help_count`. They are kept in the transaction of every write that can change them, by `writeHelpCounts`/`recountHelp` of `help-history.ts`: the workflow engine after every move whose two states differ in counting (or that changes whose a counted application is), whatever the transition (`recountAfterMove` in `workflow/engine.ts`); a merge and its revert for both profiles (`beneficiary-merges.ts`). A project's close and reopen move no application yet (the `project.closed` trigger and `applications.restore_prior_state` are not built), so they recount nothing; the move that builds them recounts the people it touches. The recount locks the person's rows in id order first and then counts in a new statement, so it never counts from a snapshot older than another writer's committed change, and writes only a counter that differs. The nightly job `jobs/help-counters.ts` on the `help-counters` queue (03:00 Dhaka time) walks every profile by id in batches of 2,000, each in its own transaction, counts the same way without a lock, hands only the profiles whose counter differs to the locked recount, logs a warning with the number repaired, and writes nothing on a second run. The counting runs with PostgreSQL's JIT off for its own statements (the setting put back afterwards): the recursive query over the merges is estimated far above the rows it reads, and the JIT compilation cost about 0.8 s of a 20 ms statement (docs/testing/PERFORMANCE.md, "The times helped"). A write of the counters alone is no edit of the person: the recount marks its one UPDATE with `css.help_counts_only = on` and clears it after, and the update-stamp trigger of the table (`beneficiaries_set_updated_at`, which keeps the name keys' rule of `css.match_keys_only`) then keeps `updated_at`, the profile's version for If-Match, as it was; any other write of the same transaction still stamps the row. The migration adds the columns with a constant default (no table rewrite), counts everyone from what is on file in one UPDATE under the same mark, and adds the indexes (help_count, id) WHERE merged_into_id IS NULL (the order, read backwards for the most first) and (id) WHERE max_helps_in_year > 1 AND merged_into_id IS NULL (the filter); timed on the measurement data set in docs/testing/PERFORMANCE.md. The rollback (`down.sql`) drops the indexes, the CHECK and the two columns and gives the table the trigger function of the name keys again; the counters are derived, so nothing a person wrote is lost.

## 18. BD-03: beneficiary mobile must not be the submitting volunteer's mobile

Enforcement in two layers (BR-008):

1. **Service** (friendly error first): when an application is created, linked or edited, and when a beneficiary's mobile changes, the application service compares the beneficiary mobile with the owner volunteer's `users.mobile` and with the creating user's mobile; on match it returns the validation error `beneficiary_mobile_is_volunteer_mobile` with the field.
2. **Database backstop**: one PL/pgSQL function `check_beneficiary_mobile_not_volunteer(application_id)` raising SQLSTATE `23514` with the message key, called by three **constraint triggers** (`DEFERRABLE INITIALLY DEFERRED`, so multi-row transactions are checked at commit):
   - `applications` AFTER INSERT OR UPDATE OF beneficiary_id, owner_volunteer_id, created_by_user_id, status — for the row, when status <> 'deleted';
   - `beneficiaries` AFTER UPDATE OF mobile — for every non-deleted application of that beneficiary;
   - `users` AFTER UPDATE OF mobile — for every non-deleted application owned or created by that user.

   The check: `beneficiaries.mobile` equals `users.mobile` of the owner volunteer's user, or of `created_by_user_id`. Public-link applications (no owner, no creator) are not checked. A beneficiary without a mobile (NULL, D-172) and a user without one never match: `=` is not true for NULL, so the function needed no change when the column became nullable, and a number given later to such a beneficiary is checked like any other.

Rationale for triggers rather than a CHECK: the two values live in different tables; PostgreSQL CHECK constraints cannot reference other rows. Tests (T2.2): direct SQL insert violating the rule fails; service path returns the friendly error; mobile change on either side is caught.

## 21. Soft delete policy

- Nothing of business value is hard-deleted (constitution §2, BR-207). The application database role has **no DELETE privilege** on business tables, with one exception: three kinds of project setup rows, `fund_sources`, `project_areas` and `dawah_syllabus_topics`, which the project setup removes only while nothing refers to them (the foreign keys refuse a used row) and audits with their before state (DECISION_LOG D-106).
- Allowed "deleted" states: `applications.status = 'deleted'` with `deleted_at` (only drafts and pending applications, by the owner or an official with the permission; BR-091); `files.deleted_at` only for `kind = 'export'` (regenerable).
- Ending instead of deleting: `revoked_at` (roles, permissions, sessions, push subscriptions), `ended_at` (project staff and volunteer assignments), `removed_at` (team members), `released_at` (blocklist), `active = false` (locations, reference lists, templates, programs), `deactivated_at` (users), `reverted_at` (merges).
- Technical rows the system may delete: expired `otp_codes`, expired unfinalized `upload_sessions`, export files after 30 days (O-30), expired unsubmitted `registration_drafts` with their photo `files` rows (D-082). These deletions are performed by jobs running under a dedicated role with DELETE only on those tables; the drafts and their photos only through the `SECURITY DEFINER` function `purge_expired_registration_drafts`, so the role has no DELETE on `files`; the expired unfinalized upload sessions through `purge_expired_upload_sessions(limit)`, which returns their ids so the nightly sweep removes the stored parts.

## 22. Retention, partitioning and archiving

- **Retention** is permanent for all business data, logs, photos and documents (BD-46). Storage growth is reported nightly (`storage_stats`).
- **audit_log**: declarative RANGE partitioning by month on `created_at` from the first migration (PROPOSAL; cheap now, very costly to retrofit). A monthly job creates the next partitions ahead of time. Old partitions are never dropped; they may be moved to a slower tablespace and become read-only. Queries by entity or person use per-partition indexes; the viewer always filters by a date range to prune partitions.
- **notifications, outbound_messages, field_changes**: start unpartitioned; convert to monthly partitions when a table exceeds about 20 million rows or 20 GB (PROPOSAL threshold), watched through `storage_stats`.
- **files**: not partitioned; rows are small and the bytes live in MinIO; object storage growth is the concern and is reported per bucket and project.
- **application_answers**: not partitioned; indexed by application; expected to stay within tens of millions of rows over many years.
- **Archiving**: no archive deletion. Closed projects stay in the same tables (read-only by the workflow guards); reports filter by year. Backups and restore drills follow O-06 (RPO 24 h → 1 h with WAL, RTO 4 h, monthly drill).
